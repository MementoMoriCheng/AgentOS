## 1. 定位与职责

### 1.1 在总体架构中的位置

GNEX 2.0 平台采用五层技术架构 + 双横切设施。数据层是第五层：

```
① 接入层 ───  API Gateway
② 控制层 ───  Agent 引擎 · 沙箱调度器 · 认证服务 · Agent注册与能力管理 · 运营管理服务 · 状态同步器
③ 网关层 ───  模型网关 · A2A 网关
④ 执行层 ───  沙箱池
⑤ 数据层 ───  缓存数据库 · 结构化数据库 · 检索数据库 · 对象存储 · 向量数据库
────────────────
横切设施 ───  消息总线（贯穿②↔④异步通信） · 可观测性（贯穿全链路）
```

**数据层 = 第⑤层**，包含五个存储组件。数据层是**被动存储层**——接收来自控制面（Agent 引擎、状态同步器）、执行面（沙箱）的写入，自己不主动拉取或消费消息总线事件。**消息总线是横切设施**，不属于数据层职责范围。

### 1.2 与其他层的交互

| 上游消费者 | 交互方式 | 关键接口 |
|---|---|---|
| **控制面（Agent 引擎）** | 热路径通过 StateInterface SDK 同步读写缓存数据库 | `StateInterface`（数据层提供） |
| **控制面（Agent 引擎）** | 冷路径异步发布事件到消息总线（由状态同步器消费后物化到数据层） | 消息总线接口（横切设施提供，控制面使用） |
| **状态同步器（控制面）** | 消费消息总线事件后，写入数据层存储（CQRS 投影） | 消息总线接口 → 数据层各存储 |
| **控制面（Agent注册与能力管理/运营管理服务）** | 通过各自的 Mapper 直连读写结构化数据库 | 各服务自持 Mapper |
| **执行面（沙箱）** | 文件产物通过 FileStoreInterface 写入对象存储 | `FileStoreInterface`（数据层提供） |

**数据流向总览**：

```
Agent 引擎 ──StateInterface──→ 缓存数据库（热·同步直连）
Agent 引擎 ──→ 消息总线（横切设施）──→ 状态同步器（控制面）
                                            │
                                            ├──→ 结构化数据库（温·checkpoint/成本/质量）
                                            └──→ 检索数据库（冷·审计归档）

沙箱 ──FileStoreInterface──→ 对象存储（文件·半同步）
管理服务 ──Mapper──→ 结构化数据库（温·同步）
```

**关键**：数据层（五个存储组件）是被动写入的目标，不主动消费消息总线事件。事件消费由状态同步器（控制面）执行——状态同步器调用数据层提供的 `SearchInterface` / `StateInterface` 等接口写入。数据层不拥有也不维护状态同步器。消息总线的接口定义与运维不归数据层，数据层文档不对其展开。

### 1.3 职责边界

**数据层负责**：

| 职责域 | 说明 |
|---|---|
| **存储运维** | 五个存储组件的选型、部署、容量规划、健康监控、备份恢复 |
| **物理 Schema 管理** | 将业务模块定义的领域实体翻译为 DDL、迁移脚本、索引策略、分区方案。数据层不理解"这个字段的业务含义是什么"，但负责"怎样让它存得高效、查得快" |
| **共享接口** | 定义并实现 `StateInterface` / `FileStoreInterface` / `SearchInterface` / `VectorStoreInterface` / `MemoryStoreInterface`，供上游业务模块和状态同步器调用 |
| **多租户隔离** | Redis ACL、PG RLS、MinIO IAM、ES DLS 等各层隔离的实现与保障 |
| **数据生命周期** | 各层 TTL 策略、自动清理、冷热数据流转 |
| **可恢复性** | 存储层自身的备份恢复、幂等性保障 |

**数据层不负责**（归控制面或其他设施）：

| 职责域 | 谁负责 | 说明 |
|---|---|---|
| **领域建模** | 控制面（Agent 引擎 / 运营管理服务） | 实体叫什么名字、有哪些字段、字段类型、实体之间的关系、约束规则——这些由业务模块定义 |
| **消息总线的建设与运维** | 消息总线团队（横切设施） | 数据层不接触消息总线 |
| **消费消息总线事件** | **状态同步器**（控制面） | 状态同步器从消息总线拉取事件，调用数据层提供的接口写入。数据层是被写入方，不消费事件 |
| **CQRS 投影逻辑** | **状态同步器**（控制面） | 从事件到各存储的物化路由、按 `event_type` 分发、聚合逻辑——这些由状态同步器执行。它调用的 `Mapper.insert()` / `SearchInterface.index()` 等接口由数据层实现 |
| **业务语义与权限判定** | 控制面（Agent 引擎 / 认证服务 / 运营管理服务） | 数据的含义、访问控制规则、事件产生时机 |

**数据流向视角**：

```
控制面（状态同步器，不归数据层）                   数据层（五个存储组件）
──────────────────────────────────              ──────────────────────────
消费消息总线事件                                 提供接口的被写方
路由 event_type → 对应投影管道                    缓存数据库（StateInterface）
调用 SearchInterface/StateInterface 写入  ──→    结构化数据库
                                                检索数据库（SearchInterface）
                                                对象存储（FileStoreInterface）
                                                向量数据库（VectorStoreInterface）
```

## 2. 设计原则

| # | 原则 | 说明 |
|---|---|---|
| **P1** | **面向接口，隐藏实现** | 跨服务共享的能力通过接口抽象（`StateInterface`、`FileStoreInterface` 等），更换存储引擎时业务代码零改动（§4） |
| **P2** | **全组件可移植** | **五个存储组件均支持引擎切换，业务代码不感知**。每一类存储通过对应的接口抽象，只暴露引擎中立的技术能力，不暴露引擎原语，也不耦合业务域概念。切换引擎 = 换一个实现类（§5） |
| **P3** | **分层存储，按需选型** | 数据按访问频率分热（缓存数据库）、温（结构化数据库）、冷（检索数据库）、文件（对象存储）、向量（向量数据库）五层 |
| **P4** | **事件驱动，状态外化** | 状态变更通过消息总线流转（不归数据层管）。状态同步器消费事件并物化结果到数据层各存储。控制面进程不持有持久状态 |
| **P5** | **隔离先行，不可绕过** | 租户隔离在数据层每一层强制生效（Redis ACL / PG RLS / MinIO IAM），不依赖应用层"传对" |
| **P6** | **一次做对，减少返工** | 接口设计一次性到位（StateInterface、FileStoreInterface、SearchInterface、VectorStoreInterface），避免接口修改导致上层返工。底层引擎可在满足性能阈值后切换，接口不变 |

## 4. 业务模块与数据层的交互规范

### 4.1 核心原则：每服务自持数据，共享能力走接口

数据层遵循微服务最佳实践——**每个微服务持有自己的 Mapper 和数据库访问代码，不集中到 `libs/`**。`libs/` 只承载两样东西：共享基础设施（数据库方言、建表 SQL、拦截器、加密）和跨服务的公共接口（文件存储、热状态、全文检索、向量检索、记忆存储）。

### 4.2 两类数据访问方式

**A. 各服务自持的 Mapper（结构化数据库的 CRUD）**

每个微服务在自己的模块中持有 MyBatis-Plus Mapper，直接读写结构化数据库。这是每个服务自己的事，不通过 `libs/` 或 `contracts/` 中转。

服务内的 `application.yml` 配置自己的 `spring.datasource`。切换数据库（SQLite → PG）时改 URL 即可——DatabaseDialect（在 `gnex-persistence-common`）自动适配方言。业务代码中的 Mapper 接口通过 MyBatis-Plus 的跨方言 SQL 生成机制保证可移植性。

**B. 跨服务的公共接口（gnex-contracts）**

只有真正需要被多个服务共享的能力，才在 `gnex-contracts` 中定义接口：

| 接口 | 定义位置（目标） | 定义位置（当前） | 实现位置 | 用途 | 当前状态 |
|---|---|---|---|---|---|
| **StateInterface** | `contracts/state/` | `contracts/state/`（当前为 `StatePort`） | `persistence-common/` | 引擎中立缓存能力（KV / List / 分布式锁） | 🔲 待重命名 + 收敛为技术缓存抽象 |
| **FileStoreInterface** | `contracts/store/` | `persistence-common/store/`（当前为 `FileStorePort`） | `persistence-common/` | 文件读写与目录管理 | ✅ 接口已有（待重命名 + 迁入 contracts） |
| **MemoryStoreInterface** | `contracts/store/` | `persistence-common/store/`（当前为 `MemoryStorePort`） | `persistence-common/` | 记忆存储与多维度检索 | ✅ 接口已有（待重命名 + 迁入 contracts） |
| **SearchInterface** | `contracts/store/` | — | `persistence-common/` | 全文索引写入与检索 | 🔲 待创建 |
| **VectorStoreInterface** | `contracts/store/` | — | `persistence-common/` | 向量嵌入存储与语义检索 | 🔲 待创建 |

**接口粒度原则**：数据层接口只表达**引擎中立的技术能力**（what 能力，而非具体引擎的 how，也非上层的业务语义 domain）。例如 `StateInterface.append(key, value, ttl)` 而非 `StateInterface.lpush(key, val)`（不暴露引擎原语），也不是 `StateInterface.saveSessionMessages(...)`（不耦合业务域）；`SearchInterface.search(index, query)` 而非 `SearchInterface.esSearch(dsl)`。业务语义（会话/沙箱/checkpoint）由上层域在技术接口之上封装。切换引擎 = 换一个实现类，接口不变。

### 4.3 接口设计

#### 4.3.1 StateInterface（缓存数据库抽象）

> **设计说明**：`StateInterface` 是**纯技术缓存抽象**，只暴露引擎中立的 KV / List / 分布式锁能力，**不耦合任何业务域概念**（不含 session / sandbox / checkpoint，也不 import `ReActCheckpoint` / `SandboxInfo` 等上层类型）。这样 L0 基础层最稳定、依赖最少，且天然满足接口隔离（ISP）与依赖方向正确。会话消息（List 语义）、会话上下文（KV 语义）由 Agent 域在其之上组合；checkpoint 属持久化，归 Agent 域 `ReActCheckpointService`（JdbcTemplate）；沙箱注册归沙箱运行时 `RedisSandboxRegistry`。迁移时将 `StatePort` 重命名为 `StateInterface` 并收敛为技术方法；值统一为不透明 `String`（调用方负责序列化与 key 命名）。

```java
// gnex-contracts/state/StateInterface.java（目标设计：纯技术缓存抽象）
public interface StateInterface {

    // ── KV（隐藏 Redis SET/GET/DEL）──────────────────────
    void put(String key, String value, Duration ttl);
    Optional<String> get(String key);
    void delete(String key);
    boolean exists(String key);

    // ── List：append + 最近 N 读（隐藏 Redis LIST 操作）──
    void append(String key, String value, Duration ttl);
    List<String> range(String key, int limit);

    // ── 分布式锁（token 安全，隐藏 Redis SET NX PX + Lua CAS）──
    Optional<String> tryLock(String key, Duration ttl);  // 获取成功返回锁 token
    boolean unlock(String key, String token);            // token 匹配才释放（CAS）

    // ── 元信息 ──────────────────────────────────────────
    String backendName();
}
```

**与当前 `StatePort` 的关系**：

| StatePort 方法 | StateInterface 对应 | 变化说明 |
|---|---|---|
| `putSessionAttribute(tenantId, sessionId, key, value, ttl)` | `put` / `append` | 泛化为技术 KV / List 操作；会话语义上移 Agent 域 |
| `getSessionAttribute(tenantId, sessionId, key)` | `get` / `range` | 同上 |
| `deleteSessionAttributes(tenantId, sessionId)` | `delete` | 按 key 删除 |
| `saveCheckpoint` / `loadCheckpoint` | **移除** | checkpoint 属持久化，归 Agent 域 `ReActCheckpointService`（JdbcTemplate），不在缓存抽象 |
| `backendName()` | `backendName()` | 签名不变 |
| — | `tryLock` / `unlock` | 通用技术锁（不耦合业务）；token 安全（tryLock 返回 token，unlock 按 token CAS 释放） |
| ~~`registerSandbox` / `heartbeatSandbox`~~ | **不纳入** | 沙箱注册归沙箱运行时 `RedisSandboxRegistry`，不在数据层 |

## 5. 全组件可移植性

### 5.1 核心结论

**数据层的五个存储组件，全部支持引擎切换，业务代码不感知**。每一类存储有对应的接口，只暴露引擎中立的技术能力，不暴露引擎原语，也不耦合业务域概念。切换引擎 = 换一个实现类，接口不变。

### 5.2 五组件可移植性总览

| 组件 | 抽象接口 | 接口暴露什么 | 接口隐藏什么 | 默认引擎 | 可替换为 | 当前状态 |
|---|---|---|---|---|---|---|
| **结构化数据库** | `DatabaseDialect`（方言）+ 各服务自持 Mapper | Schema 迁移、分页语法、类型映射 | SQL 方言差异、`AUTOINCREMENT vs BIGSERIAL` | PostgreSQL 16 | SQLite / openGauss / 达梦 DM8 | ✅ 已落地 |
| **缓存数据库** | `StateInterface` | KV / List / 分布式锁（技术能力） | Redis 命令集、Lettuce 连接池 | Redis 7.x | Hazelcast / Memcached / 进程内存 Map | 🔲 接口待重命名+收敛 |
| **对象存储** | `FileStoreInterface` | 文件读写、目录列表 | S3 SDK、Bucket 策略 | MinIO | AWS S3 / 阿里云 OSS / 本地文件系统 | ✅ 接口已有（待重命名+迁入 contracts） |
| **检索数据库** | `SearchInterface` | 索引写入、全文检索 | ES DSL / PG `tsvector` 语法 | PG `tsvector` + GIN | Elasticsearch / OpenSearch | 🔲 待创建 |
| **向量数据库** | `VectorStoreInterface` | 向量写入、相似度检索 | pgvector `<=>` 操作符 / Milvus SDK | pgvector | Milvus / Qdrant | 🔲 待创建 |

**结构化数据库的移植性不在接口而是在配置层**：每个微服务持有自己的 Mapper，切换数据库时改 `spring.datasource.url` 即可——`gnex-persistence-common` 中 `DatabaseDialect` 自动探测方言，MyBatis-Plus 的跨方言 CRUD 和分页适配保证 Mapper 代码不变。

**关键约束**：
- 接口在 `gnex-contracts` — 零引擎依赖（不 import Jedis、ES SDK、S3 SDK）

- `SearchInterface` 的 `SearchQuery` 参数是数据层自有的查询模型（含 keyword、filter、dateRange），不是 ES `QueryBuilder` 或 PG `tsquery`

### 5.4 结构化数据库可移植性（已落地）

结构化数据库的可移植性是五组件中最复杂的（涉及 DDL 迁移、分页语法、类型映射），也是当前唯一已落地的。

#### 5.4.1 方言自动探测

```java
// DialectConfig.java（当前已实现）
private static final List<DatabaseDialect> CANDIDATES = List.of(
    new SqliteDialect(),        // url.contains("sqlite")
    new PostgresDialect()       // url.contains("postgresql")
```

**新增数据库只需三步**：
1. 实现 `DatabaseDialect` 接口（~100 行）
2. 注册到 `DialectConfig` candidates 列表（1 行）
3. 通过 Squash + Convert 工具生成迁移脚本

#### 5.4.2 三层可移植性保障

```
业务代码 → MyBatis-Plus Mapper（各服务自持，零 XML）
          → MyBatis-Plus BaseMapper（框架保证跨方言 CRUD + 分页）
          → DatabaseDialect（方言适配器：tableExists / columnExists / 迁移路径）
          → SQLite / PostgreSQL / openGauss / 达梦
```

#### 5.4.3 SQL 兼容性保障

| SQL 类型 | 兼容策略 |
|---|---|
| 标准 CRUD | MyBatis-Plus `BaseMapper` 自动生成（框架保证跨方言兼容） |
| 分页查询 | `PaginationInnerInterceptor(dialect.getPaginationDbType())`（自动适配 LIMIT/ROWNUM） |
| `@Select` 注解 SQL | 仅使用标准 SQL，**禁止** `sqlite_master` / `PRAGMA` / `@@` / `${}` |
| 复杂查询 | 优先 `LambdaQueryWrapper`（框架翻译为方言 SQL） |

### 5.5 其他组件可移植性约束（待落地）

#### 5.5.1 缓存数据库

`StateInterface` 是唯一入口。接口方法为引擎中立的技术能力，如 `append(key, value, ttl)` 而非 `lpush(key, values)`（也不耦合业务语义，会话消息由 Agent 域在其上封装）。当前切换路径：`InMemoryState`（开发） → `RedisState`（生产） → 未来可换 `HazelcastState`。

#### 5.5.2 检索数据库

`SearchInterface` 是唯一入口。`SearchQuery` 是自有查询模型（keyword + termFilters + dateRange），不绑定任何引擎语法。当前切换路径：`PgTsvectorSearchImpl`（阶段一，零新增服务） → `EsSearchImpl`（阶段二，审计日志 > 5000 万行时触发）。

#### 5.5.3 向量数据库

`VectorStoreInterface` 是唯一入口。接口暴露 `upsert(id, embedding, metadata)` + `search(vector, topK)`，不暴露 `SELECT ... ORDER BY embedding <=> ?`（pgvector）或 `MilvusClient.search()`。当前切换路径：`PgvectorImpl`（阶段一，零新增服务） → `MilvusImpl`（阶段二，向量 > 500 万时触发）。

#### 5.5.4 对象存储

`FileStoreInterface` 已是唯一入口。S3 API 是行业标准，`LocalFileStore` → `S3FileStore` → 阿里云 `OssFileStore` 切换时接口不变。

#### 5.5.5 结构化数据库的分析引擎

结构化数据库承载两类查询：(a) OLTP 点查（Session CRUD、配置读写）和 (b) OLAP 聚合（Token 计费汇总、成本/质量分统计）。两者共享同一 PostgreSQL 实例，但 (b) 通过 TimescaleDB 扩展来优化。

**TimescaleDB**（默认）：PG 扩展（`CREATE EXTENSION`，零新进程），通过 hypertable 自动时间分区 + 列存压缩 + 连续聚合物化视图支撑分析型查询。

**Apache Doris**（备选）：独立 OLAP 列存数据库，与 PG 共存。Doris 是纯列存 OLAP 引擎，无法替代 PG 的 OLTP 能力（行级点查、高频 UPDATE、ACID 事务、唯一约束），因此"一步到位"的真实代价是"在 PG 之上再加一个 Doris"（3 FE + 3 BE + CDC 管道），而非替代 PG。

| 引擎 | 角色 | 适用场景 | 切换触发条件 |
|---|---|---|---|
| **TimescaleDB**（默认） | PG 扩展，OLTP+OLAP 统一引擎 | 中大规模（< 1 亿行 token_usage） | — |
| **Apache Doris**（备选） | 独立 OLAP 列存数据库，与 PG 共存 | 超大规模分析（数十亿行级聚合） | 三点全满足（见下） |

**Doris 切换触发条件**（沿用总体架构 §10.5）：
1. `token_usage` 单表 > 1 亿行，且聚合查询 P99 > 5s
2. `agent_run_event` > 5000 万行，且层级 CTE 查询影响 OLTP 延迟
3. 已有独立平台运维团队

三点 **全部满足** 才启动切换。切换时保持 PG 在线承担 OLTP，Doris 仅承担分析查询。分析查询代码从 PG Mapper 切换到 Doris Mapper，接口层不变。

**结论**：Doris 是正确的备选方案，但不应该在今天引入。现在用 TimescaleDB，未来跨过阈值后切到 Doris——这两步之间没有浪费。TimescaleDB 是 PG 的一个开关，开则加速分析，关则无损回退。Doris 不是独立组件——它是结构化数据库分析引擎的可替换项。

## 6. 存储组件选型

### 6.1 选型总览

| 组件 | 选型 | 抽象接口 | 开发环境替代 | 切换时业务层是否感知 |
|---|---|---|---|---|
| **缓存数据库（热）** | Redis 7.x | `StateInterface` | 进程内存 Map（`InMemoryState`） | **不感知** |
| **结构化数据库（温）** | PostgreSQL 16 + TimescaleDB | `DatabaseDialect` | SQLite | **不感知** |
| **检索数据库（冷）** | PG `tsvector` → ES 8.x | `SearchInterface` | PG `tsvector` + GIN（阶段一即生产可用） | **不感知** |
| **对象存储（文件）** | MinIO（S3 Compatible） | `FileStoreInterface` | `LocalFileStore`（`~/.gnex/`） | **不感知** |
| **向量数据库（向量）** | pgvector → Milvus | `VectorStoreInterface` | pgvector（阶段一即生产可用） | **不感知** |

### 6.2 缓存数据库：Redis

**用途**：会话 messages 热状态、沙箱注册表、分布式锁、文件 URL 引用、HITL 挂起状态、JWT 黑名单。

**Key 命名规范**：`{tenant_id}:{domain}:{resource_id}:{sub_resource}`

```
t_001:session:sess_abc123:messages          → List（LPUSH/LRANGE）
t_001:session:sess_abc123:context           → Hash（HSET）
t_001:sandbox:sb_456:status                 → Hash（心跳 EXPIRE 续期）
t_001:lock:session:sess_abc123              → String（SET NX EX，30s）
t_001:quota:monthly:tokens                  → String（INCRBY + EXPIREAT）
```

**缓存失效**：全部 key 设 TTL。未命中时降级到结构化数据库读。

**可移植性约束**：业务代码只能通过 `StateInterface` 接口操作缓存，禁止直接使用 Redis `SET/GET/HSET` 命令。切换引擎时仅需换实现类（`InMemoryState` → `RedisState` → `HazelcastState`），接口不变。

### 6.3 结构化数据库：PostgreSQL / SQLite

**选择 PostgreSQL 而非 MySQL 的核心理由**：

| 维度 | PostgreSQL | MySQL |
|---|---|---|
| 递归 CTE | ✅ 原生支持（`agent_run_event` 层级查询必需） | 8.0+ 才支持 |
| 向量扩展 | ✅ pgvector（零新增服务） | ❌ 无内置 |
| 全文搜索 | ✅ `tsvector` + GIN（零新增服务充当检索数据库） | 需 N-gram 解析器 |
| 行级安全 | ✅ RLS（数据库引擎层强制隔离） | ❌ 无等价机制 |
| 方言兼容性 | 与 SQLite 差异小 | 与 SQLite 差异大 |
| 分析能力 | ✅ TimescaleDB 扩展 | ❌ 需额外 OLAP 引擎 |

**SQLite 定位**：开发/测试/单租户私有部署的零配置默认库，`pool-size: 1`。

**可移植性约束**：每个微服务持有自己的 Mapper，切换数据库时改 `spring.datasource.url` + `DatabaseDialect` 自动适配，Mapper 代码无需修改。

**OLAP 分析引擎**：PostgreSQL + TimescaleDB 是当前推荐的分析引擎。TimescaleDB 是 PG 扩展，零新增服务。当数据量达到触发条件全部满足时，可切换为 Apache Doris（列存 MPP 数据库），通过切换 Mapper 实现完成迁移。Doris 不是独立组件——它是结构化数据库分析引擎的一个可替换项（详见 §5.5.5）。

### 6.4 检索数据库

**用途**：审计日志归档与全文检索、Agent 运行轨迹回放、知识库文档全文搜索。

**可移植性约束**：业务代码只能通过 `SearchInterface` 接口检索，禁止直接写 ES DSL 或 PG `tsquery`。`SearchQuery` 是数据层自有的查询模型。阶段一用 `PgTsvectorSearchImpl`（零新增服务），阶段二切换为 `EsSearchImpl`——业务代码不变。

### 6.5 对象存储：MinIO

**选择 MinIO 的理由**：S3 API 行业标准、单二进制部署、内置版本控制与加密、与 `FileStoreInterface` 语义一一对应。

**可移植性约束**：业务代码只能通过 `FileStoreInterface` 接口操作文件，禁止直接使用 S3 SDK。`LocalFileStore` → `S3FileStore` → `OssFileStore` 切换时接口不变。

**桶设计**：

| 桶名称 | 内容 | 生命周期 |
|---|---|---|
| `gnex-artifacts` | 沙箱产出文件 | 租户配额 + LRU，默认 90 天 |
| `gnex-workspace` | Workspace 快照 | session 结束后 7 天清理 |
| `gnex-documents` | 知识库文档原件 | 租户配额，永久保留 |

### 6.6 向量数据库：pgvector → Milvus

**阶段一用 pgvector**：PG 扩展，零新增服务。HNSW 索引，查询延迟 < 10ms（P99）。**阶段二用 Milvus**：触发条件——向量数 > 500 万且 P99 > 50ms。

**可移植性约束**：业务代码只能通过 `VectorStoreInterface` 接口操作向量，禁止直接写 `SELECT ... ORDER BY embedding <=> ?`（pgvector）或调用 Milvus SDK。`PgvectorImpl` → `MilvusImpl` 切换时接口不变。

### 8.2 热路径：Agent Loop 每步写入流程

```
Agent Loop（think → act → observe）
  │
  ├── PREP 步骤
  │     └── Agent 域 SessionStateService.load(...) → StateInterface.range(key, limit)
  │
  ├── THINK 步骤
  │     └── LLM 推理（经模型网关）
  │
  ├── ACT 步骤
  │     └── 下发 Action 到沙箱（WebSocket）
  │
  └── OBSERVE 步骤
        ├── Agent 域 SessionStateService.append(...) → StateInterface.append(key, msg, TTL=24h)
        └──→ 消息总线（横切设施，不归数据层）
              │
              └→ 状态同步器（控制面）消费
                   └→ 结构化数据库（checkpoint）+
                      检索数据库（审计归档）
```

### 8.3 读策略

| 场景 | 读路径 | 延迟目标 |
|---|---|---|
| Agent Loop 每步读 messages | 缓存数据库（StateInterface） | < 1ms |
| PREP 步骤知识检索 | 向量数据库（VectorStoreInterface） | < 10ms（P99） |
| 故障恢复 | 结构化数据库 checkpoint + 消息总线增量回放 | < 100ms |
| 审计回放 | 检索数据库（SearchInterface） | < 1s |
| 配置读 | Caffeine 缓存 → 结构化数据库 | < 1ms / < 10ms |

### 8.4 一致性保证

- **写后读一致**：同一 session 的热路径读写走同一缓存数据库实例（按 hash tag 路由）
- **最终一致**：消息总线 → 数据层的 CQRS 投影延迟 < 100ms。若 > 1s，直接读消息总线最新事件补齐
- **故障恢复一致**：见 §12.1 故障恢复公式

## 11. ID 生成策略

采用 **Snowflake 算法**（`IdType.ASSIGN_ID`，MyBatis-Plus 内置 `DefaultIdentifierGenerator`）。

| 维度 | Snowflake `ASSIGN_ID`（推荐） | UUID v4 | UUID v7 | 保持 `AUTO` |
|---|---|---|---|---|
| Java 类型 | `Long`（不变） | `UUID` / `String` | 同 v4 | `Long`（不变） |
| 单调性 | **递增** | 随机 | 递增 | 递增 |
| 分布式安全 | ✅ | ✅ | ✅ | ❌ 单库自增 |
| MyBatis-Plus 内置 | ✅ | ✅ | ❌ | ✅ |
| 迁移成本 | ~50 行 | **~500+ 处**（全局类型重写） | 同 v4 | 零 |

**选择 Snowflake 的三层理由**：

1. **决定性的：B-tree 写入性能**。Snowflake 的单调递增意味着新键永远追加在 B-tree 最右侧叶子页——无页分裂、缓冲池命中率高。UUID v4 的随机插入导致频繁页分裂（页使用率仅 ~70%），写入吞吐降低 20%–50%。在 `conversation_message` 和 `agent_run_event` 的高写入场景下，这是数量级的差距。

2. **工程的：最小改动路径**。45 个 Entity 改注解 vs 450+ 文件全局类型替换（`Long` → `String` 渗透到外键、Service 签名、DTO Record 和迁移脚本），改动量相差约 10 倍。

3. **辅助的：更紧凑**。8 bytes vs UUID 的 16 bytes（PG 原生 `UUID` 类型，非 `VARCHAR(36)` 的 36 bytes）。乘以 45 张表 + 60 个外键索引，在数十亿行规模下累积存储差异显著。

**Snowflake 的代价**（可控）：workerId 需多节点协调（K8s `$(POD_INDEX)` 天然解决）；时钟回拨需 NTP 配置 `ntpd -x`（slew 模式）；单节点吞吐上限每毫秒 4096 个 ID——GNEX 实际需求约 10 ID/ms。UUID v7（RFC 9562，2024）解决了 v4 的随机性但 MyBatis-Plus 无内置、外键仍需全局重写，当前不选。

**实施方案**：

| 维度 | 说明 |
|---|---|
| 类型 | `Long`（19 位），全局配置 `id-type: assign_id` |
| Worker ID | `GNEX_SNOWFLAKE_WORKER_ID` 环境变量（默认 1） |
| 前端适配 | Jackson `write_numbers_as_strings: true` → 前端 `EntityId = string` |
| 迁移兼容 | Snowflake ID 与旧 AUTO 自增 ID 可在同一 `BIGINT` 列共存，无需数据迁移 |
| 禁止项 | PMD/Checkstyle 规则禁止新代码使用 `IdType.AUTO` |
| 当前状态 | 开发环境仍使用 `id-type: auto`（SQLite 自增），切换到 PostgreSQL 时启用 `assign_id` |

## 12. 高可用与容灾

### 12.1 三层恢复协议

```
merged_state = db_checkpoint(session_id)
             + replay(mq_events_after(step=db_checkpoint.last_step, session_id))
```

| 层 | 角色 | 时效性 | 恢复速度 |
|---|---|---|---|
| ① 缓存数据库 | 加速缓存 | 最新（丢几秒） | 毫秒 |
| ② 结构化数据库 checkpoint | **权威快照**（基线） | checkpoint 时刻 | 十毫秒 |
| ③ 消息总线事件（通过状态同步器物化至数据层） | **增量补齐** | 完整 | 百毫秒 |

### 12.2 组件级容灾

| 组件 | 故障场景 | 恢复策略 | RTO |
|---|---|---|---|
| 缓存数据库 | 主节点宕机 | Sentinel 自动切换 + 结构化数据库+消息总线回灌 | < 15s |
| 结构化数据库 | 主库宕机 | 流复制 + HA Manager 自动 Failover | < 30s |
| 检索数据库 | 节点宕机 | ES 副本自动提升 | < 30s |
| 对象存储 | 节点宕机 | MinIO 纠删码（EC）自动容错 | < 5s |
| 向量数据库（pgvector）| 随 PG 故障 | 随 PG failover | < 30s |

### 12.3 幂等性

| 操作 | 幂等实现 |
|---|---|
| 文件写入 | 覆盖写，不用追加写 |
| 结构化数据库 | `INSERT ... ON CONFLICT DO UPDATE`（UPSERT） |
| 缓存数据库 | `SET` 覆盖（天然幂等） |

## 13. 容量规划

> **术语说明**：本节"并发 Session"指**平台上同时运行的 Agent 会话数**（Agent Loop 处于 think → act → observe 循环中的 session），不等同于用户浏览器连接数（一个用户可同时发起多个 Agent Session），也不等同于后端到数据层的连接池大小。该定义与总体架构 §1"同时在线 Agent"一致。

| 规模 | 并发 Session | 缓存数据库 内存 | 结构化数据库 | 消息总线 存储/天¹ | 对象存储 | 向量库 |
|---|---|---|---|---|---|---|
| **小型** | 100 | 500 MB | 5 GB | 10 GB | 10 GB | 2 GB（约 1 万篇文档） |
| **中型** | 1 万 | 5 GB（Cluster） | 50 GB | 100 GB | 100 GB | 20 GB（约 10 万篇文档） |
| **大型** | 10 万 | 50 GB（多节点 Cluster） | 500 GB | 1 TB | 1 TB | 200 GB（约 100 万篇文档） |

> ¹ 消息总线是横切设施，不归数据层运维。此列仅供参考，数据来源于总体架构 §8.8 容量规划基线。

**容量公式**：
```
缓存数据库  ≈ 并发Session × 100KB + 沙箱数 × 1KB + 10% buffer
结构化数据库 ≈ 每条Message 1KB × 日均 + 每Checkpoint 10KB × session × 频率 + 索引 50%
向量数据库   ≈ 文档数 × chunk数 × 6KB/向量（1536维）+ HNSW 索引（约向量数据 67%）
```

**动态吞吐量基线**（来源：总体架构 §4.4 消息总线性能基线，数据层各组件需满足上游写入吞吐）：

| 规模 | 消息速率（写入驱动） | 缓存数据库 读写 QPS 估算² | 结构化数据库 checkpoint TPS 估算² |
|---|---|---|---|
| **小型** | ~1K msg/s | ~2K RPS / ~1K WPS | ~100 TPS（每步 checkpoint） |
| **中型** | ~10K msg/s | ~20K RPS / ~10K WPS | ~1K TPS |
| **大型** | ~50K msg/s | ~100K RPS / ~50K WPS | ~5K TPS |

> ² QPS 估算基于：每个并发 Session 的 Agent Loop 每步产生 1 次缓存写 + 1~2 次缓存读；checkpoint TPS = 并发 Session 数 × 每秒 checkpoint 频率（默认每步，约 1 次/秒/Session）。实际值取决于 Agent 步频和 checkpoint 策略（§8.6 每步/周期/关键点），此处按"每步 checkpoint"上限估算。

## 15. 演进路线

### 15.1 核心原则

**接口不变，引擎可换。不做浪费式演进**——凡是在后续阶段会导致前期工作被丢弃的中间方案，都不做或只做轻量适配。

| 可以演进（不浪费） | 不能演进（浪费） |
|---|---|
| ✅ 同一接口下增加新引擎（LocalFileStore → S3FileStore） | ❌ 先建造一个会被整体丢弃的中间系统 |
| ✅ 从 pgvector 升级到 Milvus（VectorStoreInterface 不变） | ❌ Service 中添加不必要的中间抽象层 |
| ✅ 从 PG GIN 切换到 ES（SearchInterface 不变） | ❌ 先定义一套接口后来推翻重来 |

### 15.2 两阶段路线

```
阶段 1（当前 → 2.0 基础就绪）—— 接口定义 + 引擎到位 + 业务适配
─────────────────────────────────────────────────────────────
接口落地：
  🔲 StatePort → StateInterface 重命名 + 收敛为技术缓存抽象（§4.3.1）
  🔲 FileStorePort → FileStoreInterface 重命名 + 迁入 gnex-contracts/store/
  🔲 MemoryStorePort → MemoryStoreInterface 重命名 + 迁入 gnex-contracts/store/
  🔲 VectorStoreInterface / SearchInterface 接口创建
  ✅ DatabaseDialect 方言抽象（已就绪）

引擎到位：
  🔲 Redis 引入（缓存数据库，热路径读写 + 分布式锁）
  🔲 MinIO 引入（对象存储，沙箱跨节点时触发）
  🔲 pgvector 启用（向量数据库，知识库功能上线时触发）

业务层适配：
  🔲 热路径 StateInterface 替换 conversation_message 的 Mapper 直写
      当前 conversation_message 通过 ConversationMessageMapper 直写结构化数据库。
      替换为 StateInterface 后，热写走缓存数据库（Redis/内存），冷持久化仍由
      状态同步器消费消息总线事件后写入结构化数据库。替换步骤：
      1. StateInterface 实现类就绪（InMemoryState / RedisState）
      2. Agent 引擎热路径从 Mapper.insert() 切换为 Agent 域 SessionStateService（基于 StateInterface.append/range）
      3. 状态同步器消费 agent_events 后物化到结构化数据库（已有逻辑）
      4. 验证：热路径延迟 < 1ms，故障恢复公式（§12.1）可正确还原状态

  🔲 Snowflake ID 启用（id-type: auto → assign_id，随 PG 切换同步）

阶段 2（2.0 架构成型）—— 按需扩展
─────────────────────────────────────
  🔲 Elasticsearch 引入（检索数据库，审计日志 > 5000 万行时触发）
  🔲 Hybrid 记忆存储上线（PG 元数据 + MinIO 内容）
  🔲 多数据库方言扩展（openGauss / 达梦 DM8，有国产化需求时触发）
```

### 15.3 不做的事（避免浪费）

| 不做的事 | 理由 |
|---|---|
| **不建造会被丢弃的 DB-Backed 消息总线** | 消息总线不归数据层。当前 `agent_message_bus` 表是过渡方案，不做深度优化 |
| **不在阶段一引入独立向量检索服务** | pgvector 是 PG 扩展，零新增服务。`VectorStoreInterface` 一次设计到位，未来切换接口不变 |
| **不引入不必要的中间抽象层** | 保持各服务自持 Mapper 的微服务标准架构，不强加集中式 Repository |
| **不在阶段一引入 Elasticsearch** | PG `tsvector` + GIN 满足中小规模。`SearchInterface` 一次设计到位，达到阈值再切换 |

### 15.4 触发条件

阶段二的每个组件引入需满足明确的性能/规模阈值，不做预优化：

| 组件 | 阶段一方案 | 切换到阶段二的触发条件 |
|---|---|---|
| 检索数据库 | PG `tsvector` + GIN | 审计日志单表 > 5000 万行且全文搜索 P99 > 1s |
| 记忆存储 | 文件持久化（MemoryStoreInterface） | 知识库功能需要向量+元数据混合检索时触发 Hybrid 方案 |
| 多数据库方言 | SQLite / PostgreSQL | 有国产化信创需求时触发 openGauss / 达梦 DM8 |

### 15.5 未来演进方向

以下组件属于超大规模场景的演进需求，不在 GNEX 2.0 范围内。当业务规模达到触发条件时，作为后续版本数据层规划：

| 组件 | 2.0 方案 | 后续演进方向 | 触发条件 |
|---|---|---|---|
| 向量数据库 | pgvector（PG 扩展） | 独立向量数据库 Milvus/Qdrant | 向量数 > 500 万且查询 P99 > 50ms |
| 缓存数据库 | 单节点 Redis | Redis Cluster 多节点 | 内存 > 10GB 或单节点 QPS > 50000 |
| 结构化数据库 | 单节点 PG | 读写分离（读副本） | 读 QPS > 主库 70% |
| 结构化数据库（分析引擎） | TimescaleDB | Apache Doris | `token_usage > 1亿行且P99 > 5s`、`agent_run_event > 5000万行且CTE影响OLTP`、已有运维团队——三点全满足 |

**原则**：2.0 的接口设计已为后续演进预留空间——上述切换均为"同一接口下换一个实现类"，接口不变，业务代码零改动。
