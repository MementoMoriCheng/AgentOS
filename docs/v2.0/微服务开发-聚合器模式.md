# Assembler 架构说明：模块化开发，单体聚合部署

## 核心理念

**"微服务模式开发，统一聚合"**——开发时当微服务写代码，打包时当单体部署。AI 不会搞混，人也不会搞混。

```
开发时：每个模块按微服务模式开发（独立的 pom.xml、package、@SpringBootApplication、main）
部署时：assembler 聚合所有模块为一个 fat jar，统一部署
```

## 构建流程

```
gnex-agent-service ──→ agent-service.jar ─┐
gnex-platform-service─→ platform-service.jar ─┤
gnex-sandbox-runtime─→ sandbox-runtime.jar ──┤──→ gnex-dev-assembler (dependency)
gnex-state-plane-svc ─→ state-plane.jar ────┤              │
gnex-observability-svc→ observability.jar ──┘              │
                                                   spring-boot-maven-plugin
                                                           repackage
                                                            │
                                                            ▼
                                                   gnex-dev-assembler-0.1.0.jar
                                                   (一个 fat jar，含所有模块)
```

## 关键规则

| 角色 | 说明 |
|------|------|
| **各模块** | 普通 jar（plain jar），spring-boot-maven-plugin 配置 `<skip>true</skip>` |
| **assembler** | 唯一执行 repackage 的模块，产出 fat jar |
| **Flyway 迁移** | 统一放在 assembler 的 `src/main/resources/db/migration/` |
| **启动入口** | 各模块可保留自己的 `@SpringBootApplication` 用于本地测试，但最终部署以 assembler 的入口为准 |
| **模块间调用** | 直接 Java 方法调用，无网络开销 |

## 优劣势

### 优势
- 部署简单：一个 fat jar 启动所有模块
- 零网络开销：模块间直接方法调用
- 开发调试方便：IDE 里一键跑
- 资源利用率高：共享 JVM 内存

### 劣势
- 无法独立扩缩容，所有模块捆绑
- 故障不隔离：一个模块 OOM 拖垮整个进程
- 发布耦合：任何模块改动都要重新打包整个 assembler
- Flyway 迁移脚本必须集中管理，模块不能独立控制数据库版本

## 与独立微服务的区别

| 对比项 | Assembler 单体聚合 | 独立微服务 |
|--------|-------------------|-----------|
| **最终产物** | 一个 fat jar | 每个模块一个 fat jar |
| **运行进程** | 一个 JVM 进程 | 每个模块一个 JVM 进程 |
| **模块间调用** | 直接 Java 方法调用（内存地址） | 网络 HTTP/gRPC 调用 |
| **部署方式** | 一个 Docker 容器 | 每个模块一个 Docker 容器 |
| **扩缩容** | 只能一起扩缩 | 可单独对某个模块扩缩 |
| **故障隔离** | 一个模块挂了 → 整个进程挂 | 一个模块挂了不影响其他 |
| **发布耦合** | 改一行代码也要重打整个包 | 只发布改动的模块 |
| **Flyway 管理** | 统一在 assembler 管理 | 每个模块独立管理 |
| **网络开销** | 零 | 每次调用有网络延迟 |
| **资源利用率** | 共享 JVM 内存，利用率高 | 每个进程固定 overhead，总内存占用大 |

## 开发人员需要关注什么

### 1. 模块内开发（日常）
- 在自己的模块里正常写业务代码，不需要关注部署形态
- 依赖其他模块的 class，直接在 pom.xml 加 dependency 即可（因为是同一个 JVM）
- 单元测试在自己的模块内独立跑，不需要启动 assembler

### 2. Flyway 迁移脚本
- 新建迁移脚本时，**不要放自己模块的 resources/db/migration/ 下**
- 统一放到 `gnex-dev-assembler/src/main/resources/db/migration/`，按版本号命名
- 如果脚本是某个模块专属的，在文件名或文件注释中标明归属

### 3. 底座（@SpringBootApplication）
- 每个模块可以保留自己的 `@SpringBootApplication` 和 `main` 方法，用于本地独立开发测试
- 但该模块的 spring-boot-maven-plugin 必须配置 `<skip>true</skip>`，避免产出多余的 fat jar
- 全局配置（application.yml）统一放在 assembler 中，各模块的专属配置可放在自己的 resources 下

### 4. 条件装配
- 如果模块里的 bean 需要根据配置开关控制，用 `@ConditionalOnProperty`，不要用 `@ConditionalOnBean(assembler 中的某个 bean)`
- 依赖其他模块的 bean 时，优先使用 `ObjectProvider` 可选注入，避免启动顺序问题

### 5. 资源隔离意识
- 所有模块共享同一个 JVM 堆内存，注意不要写出内存泄漏的代码
- 线程池、连接池等资源要合理设置上限，避免一个模块耗尽全部资源
