# GNEX v2.0 测试机制设计

> 本文档是 v2.0 测试体系的完整设计说明书，供测试 agent 接收并执行。
> 机制不依赖 v2.0 模块拆分完成，可先于模块定型落地。

---

## 一、设计目标

### 1.1 要解决的痛点（来自 v1.0 实战）

| 痛点 | v1.0 现状 | v2.0 目标 |
|---|---|---|
| 单次跑太慢 | 每次全模块跑，60min+ | 标签精准切片，5min 跑今天新增 |
| 新功能没入口 | 要等模块全量跑 | @date 标签，当天 5min 验证 |
| bug 没闭环 | 手动整理 30min | 钩子即时建禅道 bug 30s |
| 三层无法独立 | 只有全量一个模式 | 三档各跑各的，互不阻塞 |
| 加用例成本高 | 要改 skill 配置 | 打标签写入即进回归库，零配置 |

### 1.2 满足的功能（验收标准）

机制建好后，必须能支撑以下 6 项功能：

1. **小功能级测试**：今天开发提交的新功能，5 分钟内验证完
2. **功能点级回归**：修完某个 bug，3 分钟重跑该功能的所有用例
3. **模块级测试**：按功能域跑子集（如只跑 chat 域冒烟），15 分钟
4. **全系统回归**：发布前按优先级全量跑，数小时但按复杂度收敛
5. **自动建禅道 bug**：任一 test fail，30 秒内禅道出现 bug（含证据）
6. **不停加用例**：加用例零配置，打标签写入即被任意切片命中

## 二、机制核心：三层金字塔 + 标签横切

### 2.1 核心思路

v1.0 的本质问题是「只有全量跑一个模式，没有切片能力」。v2.0 引入一个**横切维度（标签）**，让同一套用例能从任意维度切片，形成三种运行粒度。

**为什么是标签而不是目录**：目录是树状固定的（一个文件只能在一个目录），标签是多对多的（一条用例可同时属于"今天新增"+"高危"+"smoke"+"某功能点"）。需求维度是动态的，标签才能表达。

### 2.2 三层结构

- **L3 全系统**：fullstack-regression-test（编排器）— 发布前全量验证
- **L2 功能域**：domain-test x 12个 — 按域独立测试，每个有"模式A子集"+"模式B全量"
- **L1 小功能**：feature-smoke-test（跨域入口）— 跨域按 feature/date 跑

**关键**：三层不是三套用例，是同一套 .spec.ts 的三种 --grep 范围。

| 层 | grep 范围 | 耗时 | 频率 |
|---|---|---|---|
| L1 小功能 | @date:今日 或 @feature:xxx | 5-15min | 每天 |
| L2 功能域 | @domain:xxx.*@layer:smoke 或全域 | 15-30min | 部署后 |
| L3 全系统 | @layer:smoke 或无 grep 全量 | 数小时 | 发布前 |

### 2.3 与 G0.5 / G1 / G2 / G3 门禁的映射

> **重要**：本机制的 L1/L2/L3（运行粒度）与 v2-4 GATE-CRITERIA 的 G0.5/G1/G2/G3（交付门禁）是**两个正交维度**——L 层回答"这次跑多大范围"，G 层回答"这个里程碑交付到什么程度才算过"。两者必须对应清楚，否则团队无法把"跑测试"和"签收门禁"挂钩。口径以 v2-spec-integration-gate.md §2 为准。

| 运行层 | 对应门禁 | 门禁定义（见 v2-spec-integration-gate.md） | 机制怎么支撑 |
|---|---|---|---|
| L1 小功能 | G1 开发自测粒度 | G1 §2.2 的 30 子项，每项需 e2e 或 curl/grep/mvn 断言证明 | `--grep "@date:今日"` 或 `"@feature:xxx"` 跑新增用例，pass 即作为该子项证据 |
| L2 功能域 | G1 域验收 / G2 系统能力 | G1 按域签收（智能体15/沙箱5/治理4/注册2/总线1/可观测2/前端1）；G2 含双副本/恢复/性能/安全 | `--grep "@domain:xxx.*@layer:smoke"` 跑域子集，作为该域 G1 证据；G2 需补性能/安全切片（见 §7.4） |
| L3 全系统 | G3 发布门禁 | G3 §2.4：全系统端到端 0 缺陷 + 0 skip + 发布就绪 | 无 grep 全量跑，`fullstack-regression-test` 编排，产出 G3 V1（P0/P1=0）证据 |
| —（机制不覆盖） | G0.5 设计定稿 | G0.5 §2.1：编译绿 + Spec 文档齐 | 机制不参与 G0.5（此时 @domain 未冻结，机制尚未启动） |

**桥接规则**：
- G0.5 关账（@domain 冻结）前，只有 L1 可跑（用 @date/@feature，@domain 填 todo）
- G1 签收 = L2 各域 smoke 全 pass + 各服务自测报告
- G3 签收 = L3 全量 0 skip + P0/P1=0
- **L1/L2/L3 不替代 G 门禁**，而是 G 门禁断言的"执行载体"

## 三、5 维标签体系

### 3.1 标签定义

每条 test 的 title 必须包含 5 个标签：

```ts
test("@domain:governance @feature:sso-logout @layer:smoke @severity:high @date:20260630 SSO登出应清除会话", ...)
```

| 标签 | 取值 | 用途 | 何时定型 |
|---|---|---|---|
| @domain | chat / orchestration / execution / workflow / registry / governance / auth / sandbox / bus / persistence / observability / frontend（12 域，见 §3.3） | 功能域归属 | 模块拆完后冻结；拆完前填 todo |
| @feature | kebab-case 功能名，如 sso-logout / agent-routing | 功能点标识 | 永远动态，每新功能一个 |
| @layer | smoke / deep / e2e | 测试层次 | 固定三档 |
| @severity | high / mid / low | 严重度 | 固定三档 |
| @date | YYYYMMDD | 落实日期 | 永远动态，填当天 |

### 3.2 各维度解决的切片问题

| 维度 | 解决的切片问题 | 示例 grep |
|---|---|---|
| @domain | "跑某个模块的用例" | --grep "@domain:chat" |
| @feature | "跑某个功能点的用例" | --grep "@feature:sso-logout" |
| @layer | "只跑冒烟/只跑深度" | --grep "@layer:smoke" |
| @severity | "只跑高危用例" | --grep "@severity:high" |
| @date | "跑今天/本周新增的用例" | --grep "@date:20260630" |

### 3.3 @domain 与 v2.0 服务 / spec 目录的映射

v2.0 不再用 d1-d9，改用功能域（一个功能跨多个服务）。@domain 取值必须与 docs/v2.0-specs/ 的服务包子目录**双向对齐**——这样一条用例既知道跑哪个服务，也知道查哪份 spec 验收。

映射表（与 v2.0-specs/README.md 二 目录结构、TEAM-INSTRUCTIONS.md 一 分工一致）：

| @domain | 涉及 v2.0 服务 | 对应 spec 目录 | 负责人 | v1.0 来源 |
|---|---|---|---|---|
| chat | gnex-agent-service + d1-web | agent/ + frontend/ | 周小平+蔺群越+刘琨 | d2+d3+d1 |
| orchestration | gnex-agent-service | agent/ | 周小平+蔺群越 | d3+d4 |
| execution | gnex-agent-service + gnex-sandbox-runtime | agent/ + sandbox/ | 周小平+蔺群越+谭泽 | d4+d7 |
| workflow | gnex-agent-service | agent/ | 周小平+蔺群越 | d3(workflow) |
| registry | gnex-platform-service | registry/ | 匡涛 | d5 |
| governance | gnex-platform-service | ops/ | 赵海刚 | d6 |
| **auth** | gnex-auth-service | auth/ | 赵海刚 | （v1.0 散落，v2.0 独立服务） |
| sandbox | gnex-sandbox-runtime | sandbox/ | 谭泽 | d7 |
| bus | gnex-bus-service | bus/ | 程少巍 | d8 |
| persistence | gnex-platform-service + 各 service 持久层 | data/ | 赵海刚 | d9 |
| **observability** | gnex-platform-service + gnex-observability-service | observability/ | 张枭宇 | （v1.0 散落，v2.0 含 CQRS/状态外化/三层恢复） |
| frontend | d1-web | frontend/ | 刘琨 | d1 |

**v1.0 到 v2.0 的域调整说明**：
- **新增 auth 域**：v1.0 认证散落在各模块，v2.0 拆出独立 gnex-auth-service（Token/登录/SSO/APIKey/密码/设备会话），必须有独立 @domain 才能切片
- **新增 observability 域**：v2.0 状态外化（Redis会话/PG检查点/MinIO）+ CQRS 物化 + 三层恢复是 G2 硬指标，不能并入 persistence
- **governance 归 ops/**：v2.0 治理能力（RBAC/审计/计费/SSO配置/密码策略/沙箱资源）归 gnex-ops-service，spec 在 ops/ 目录
- **workflow 归 agent/**：v2.0 工作流引擎在 gnex-agent-service（非 platform-service），spec 在 agent/

> **跨域功能归属**（与 v2.0-specs/README.md 六一致）：审计事件发布归 auth/+ops/；审计消费物化归 observability/；A2A External 归 agent/；密码策略 Port 归 ops/；沙箱资源 Port 归 ops/、沙箱执行归 sandbox/；模型降级+成本预算归 agent/。

### 3.4 @domain 冻结时机（对齐 G0.5）

@domain 冻结的前置是 **G0.5 关账**（见 §2.3 映射），具体标志：

- G0.5 V1 编译绿：`mvn -q clean package -DskipTests` exit 0（services/* 全部 pom modules 定稿）
- G0.5 V5 Spec 文档齐：docs/v2.0-specs/ 各目录预期数达标（不执着份数，看覆盖度；agent/ 已有 EXECUTION-ENGINE-SPEC.md 一份聚合 spec 覆盖执行引擎全部核心，够用）
- 上述两项通过 → 冻结 @domain 取值表（12 个域，见 §3.3）→ 更新 tag-lint 的 DOMAINS 数组（去掉 todo）→ L2 域 skill 才能建

> **现状（2026-07-10）**：G0.5 已于 2026-07-09 关账（见 TEAM-INSTRUCTIONS.md §346），@domain 12 个域取值已冻结。L1/L2/L3 均可启动：
> - L1 已跑通（75 个 spec 已打 5 维标签，tag-lint 已就位）
> - L2 域 skill 可建（@domain 已冻结，tag-lint 严格门禁可开启）
> - L3 全系统回归可建
> - _shared/ 公共层可迁移（现有 75 个 spec 已有标签，不会拦截 push）

### 3.5 标签组合语义

Playwright --grep 是正则，默认 AND 语义（用 .* 连接）：
- --grep "@domain:chat.*@layer:smoke" → chat 域的 smoke（AND）
- --grep "@date:2026062[4-9]|@date:20260630" → 本周新增（OR）

语义在 _test-common 里写死，避免各 skill 不一致。

## 四、目录结构

按功能域组织，不按服务组织（测试视角是功能域）：

```
gnex-core-v2/d1-web/frontend/e2e/
├── _shared/              # 公共层（hooks/fixtures/helpers/tag-lint）
│   ├── hooks.ts          # afterEach fail 钩子（调 zentao-bug-submit）
│   ├── fixtures.ts       # loginCtx: acquire(user) -> {token, page, cleanup}
│   ├── helpers.ts        # SSE抓包(.NET HttpClient) / docker日志 / 注入LLM Key
│   └── tag-lint.js       # 标签校验脚本
├── chat/                 # 对话/SSE/预览
├── orchestration/        # Team/Room/路由/多Agent
├── execution/            # 工具执行/InspectorChain
├── workflow/             # 工作流生命周期
├── registry/             # Agent/Skill/Tool/MCP/凭证
├── governance/           # 审计/RBAC/SSO/计费
├── sandbox/              # 敏感路径/风险分级
├── bus/                  # 消息总线
├── persistence/          # 隔离/迁移/记忆
├── frontend/             # 纯UI渲染/XSS
└── cross-module/         # 跨域 E2E（只有 L3 跑）
```

一个文件多条 test，每条打不同标签：

```ts
// e2e/governance/sso-logout.spec.ts
test("@domain:governance @feature:sso-logout @layer:smoke @severity:high @date:20260630 正常登出应清除会话", ...)
test("@domain:governance @feature:sso-logout @layer:deep  @severity:mid  @date:20260630 登出后token应立即失效", ...)
test("@domain:governance @feature:sso-redirect @layer:smoke @severity:high @date:20260628 未登录访问受保护页应跳转登录", ...)
```

- --grep "@feature:sso-logout" -> 跑前两条
- --grep "@date:20260630" -> 跑前两条
- --grep "@domain:governance.*@layer:smoke" -> 跑第 1、3 条

### 5.1 skill 清单

| skill | 层 | 形态 | 状态 |
|---|---|---|---|
| _test-common | 公共 | 继承基类，加标签规范 + fail 钩子 | 改造 |

### 5.2 各 skill 职责

#### _test-common（改造）
新增两节：
- **标签规范**：5 维齐全，格式定义，缺标签=lint fail
- **fail 钩子**：afterEach fail 自动调 zentao-bug-submit

#### feature-test-author（新建）
- 定位：辅助加用例，约束 LLM 不乱写
- 输入："给 xxx 加一条用例: yyy"
- 动作：提取 feature/domain -> 模板填空 -> 自动打标签 -> tag-lint -> 写入 spec
- 约束：test body 必须 ARRANGE/ACT/ASSERT 三段；至少含 API 断言

#### feature-smoke-test（新建）
- 定位：L1 跨域入口，最高频使用
- 输入：自然语言（"测今天的新功能" / "测 sso 登出"）
- 动作：查指令翻译表 -> 拼 grep -> 跑 Playwright -> 汇总
- 内置固定的指令翻译表（非 LLM 即兴）

指令翻译表（固化）：

| 你的自然语言 | 翻译成的 grep |
|---|---|
| "测今天的新功能" | --grep "@date:<今日>" |
| "测 sso 登出" | --grep "@feature:sso-logout" |
| "测本周新增" | --grep "@date:YYYYMMDD|@date:..."（本周日期范围） |
| "测 chat 域冒烟" | --grep "@domain:chat.*@layer:smoke" |
| "重跑 xxx" | --grep "@feature:xxx" |

#### domain-test x 12（@domain 定型后建）
- 模式A（子集）：--grep "@domain:xxx.*@layer:smoke"
- 模式B（全量）：--grep "@domain:xxx"

#### fullstack-regression-test（沿用）
- 阶段 0 加标签健康检查（跑 tag-lint）
- 阶段 1-3 按优先级委托各域 skill

#### zentao-bug-submit（已存在，小改）
- 标题规范从 [d3-orchestration-P1] 改成 [domain-P1]
- 其余逻辑（node 脚本建 bug、中文编码处理、查重）不动

## 六、调用链

### 6.1 跑用例的调用链

以 "测今天的新功能" 为例：

1. 你说: "测今天的新功能"
2. 调用 feature-smoke-test skill（skill 内部, 固化逻辑, 非 LLM 即兴）
3. skill 翻译指令：查指令映射表 -> 算今日日期 -> 拼 --grep "@date:20260630" -> 拼 npx playwright test 命令
4. 执行 Playwright 命令
5. Playwright 扫描所有 .spec.ts 文件，对每条 test 用正则匹配 title 是否含 @date:20260630
6. Playwright 逐条执行匹配到的 test：
   - beforeEach: 登录 + 注入LLM Key + 初始化（由 _shared/fixtures 提供）
   - test body: 你写的断言逻辑
   - afterEach: fail 检测 -> 触发禅道钩子
   - 清理
7. 某 test 结果：pass -> 继续；fail -> 触发禅道钩子（见 6.3）

**关键**：skill 不知道有哪些用例、在哪个文件。它只给 grep 参数，Playwright 自己匹配。

### 6.2 加用例的调用链

以 "给 sso 登出加一条: 登出后 token 立即失效" 为例：

1. 你说: "给 sso 登出加一条用例: 登出后 token 立即失效"
2. 调用 feature-test-author skill
3. skill 做四件事:
   a. 定位文件: 查 @feature:sso-logout 已有文件（已存在则追加，首次出现则新建）
   b. 生成 test 骨架: 模板填空（LLM 只填 ACT/ASSERT 代码）
   c. 自动打标签:
      - @domain: 从文件所在目录推断
      - @feature: 你说的功能名
      - @layer: LLM 建议（只查API=smoke, 查状态=deep, 查UI=e2e）
      - @severity: LLM 建议（安全相关=high, 功能正常=mid, 体验=low）
      - @date: 自动填今天
   d. tag-lint 校验: 5维齐全? 格式正确? -> 通过才写入
4. 写入 .spec.ts 文件（追加 test 到现有文件）
5. 立即可跑（无需任何注册/配置）：--grep "@feature:sso-logout" -> 新加的这条自动被匹配
6. 这条用例从此进入用例库，后续任意切片都能命中

### 6.3 fail 闭环的调用链

某条 test fail 时：

1. Playwright 检测到 test fail
2. 触发 afterEach 钩子（由 _shared/hooks.ts 提供, 所有 test 自动继承）
3. 钩子收集证据:
   a. 读 test-results/<case-id>/error-context.md 的 page snapshot（E3铁律: 先看DOM）
   b. 截图: test-results/<case-id>/test-failed-*.png
   c. docker logs: ssh 取 gnex-core-v2-dev-web 最近50行
   d. SSE 抓包: 若涉及流式, 取 .NET HttpClient 抓的字节流
4. 钩子解析 test title 提取标签 -> domain, feature, severity
5. 轻量判断: 是测试代码问题 or 系统bug?
   - 看 error message 是否含 locator/selector/expect.toBe 等测试框架关键词
   - 是 -> 报"测试代码问题", 不提 bug
   - 否 -> 调用 zentao-bug-submit skill
6. zentao-bug-submit skill 建 bug:
   - 标题: [governance-P1] 登出后token应立即失效
   - severity: high->1, mid->2, low->3
   - steps: [步骤][结果][期望][证据] 四段
   - 用 node 脚本提交（避免中文乱码）
7. 禅道返回 bug URL
8. 钩子把 bug URL 写入测试报告

## 七、关键环节详解

### 7.1 feature-test-author：怎么辅助生成 test 骨架

#### 约束 LLM 的三大约束

| 约束 | 机制 | 效果 |
|---|---|---|
| **模板固化结构** | test body 必须 ARRANGE/ACT/ASSERT 三段, LLM 只填 ACT/ASSERT 代码 | LLM 不能改用例骨架 |
| **断言分层强制** | 至少含 L1 API 断言 (expect status), L2/L3 按需 | 防止弱断言 |
| **标签自动填** | domain/feature/date 自动推断, layer/severity LLM 建议+你确认 | 防止标签遗漏 |

#### 模板（固化）

```ts
test("@domain:{domain} @feature:{feature} @layer:{layer} @severity:{severity} @date:{date} {scenario}",
  async ({ request, loginCtx }) => {
    // === ARRANGE: 前置准备 ===
    const ctx = await loginCtx.acquire("admin");
    const token = ctx.token;

    // === ACT: 执行被测动作 ===
    // LLM 填: 调哪个 API / 点哪个按钮

    // === ASSERT: 断言 (三层, 必须含至少一层) ===
    // L1 API断言 (必有): expect(res.status()).toBe(200);
    // L2 状态断言 (按需): 查后端状态/DB
    // L3 UI断言 (按需): 查页面渲染
  });
```

LLM 只填这 5 个空：domain（已定）、feature（已定）、layer、severity、ACT/ASSERT 代码（结构固定，只填实现）

#### 实例输出

输入："给 sso 登出加一条: 登出后 token 立即失效"

输出：

### 7.2 禅道钩子：挂哪里

#### 选 afterEach，原因

| 位置 | 触发时机 | 即时建 bug | 选不选 |
|---|---|---|---|
| **afterEach** | 每条 test 结束 | **能, 即时** | **选** |
| globalTeardown | 整个测试跑完 | 不能, 要等全部跑完 | 不选 |
| reporter | 每条 test 结束 | 能, 但逻辑更绕 | 不选 |

#### 落地：_shared/hooks.ts

```ts
// e2e/_shared/hooks.ts (由 _test-common 提供)
import { test as base } from "@playwright/test";

// 自动 afterEach: fail 时建禅道 bug
export const test = base.extend({}).afterEach(async ({}, testInfo) => {
  if (testInfo.status !== "failed") return;  // 只处理 fail

  // 1. 解析标签 (从 title 提取)
  const title = testInfo.title;
  const tags = parseTags(title);  // { domain, feature, layer, severity, date }
  if (!tags) {
    console.warn("[钩子] 标签不全, 跳过建 bug: " + title);
    return;
  }

  // 2. 收集证据
  const traceDir = "test-results/" + testInfo.testId;
  const errorCtx = readIfExists(traceDir + "/error-context.md");
  const snapshot = extractPageSnapshot(errorCtx);  // E3 铁律: 先看 DOM
  const screenshot = findScreenshot(traceDir);
  const logSnippet = await fetchContainerLogs();  // docker logs 最后50行

  // 3. 轻量判断: 测试代码问题 or 系统bug?
  if (isTestCodeIssue(testInfo.error?.message)) {
    console.warn("[钩子] 测试代码问题, 不提 bug: " + title);
    return;
  }

  // 4. 调用 zentao-bug-submit skill 建 bug
  // (skill 内部用 node 脚本提交, 避免中文乱码)
  const bugUrl = await submitZentaoBug({
    title: "[" + tags.domain + "-P" + mapSeverity(tags.severity) + "] " + stripTags(title),
    severity: mapSeverity(tags.severity),  // high->1, mid->2, low->3
    steps: buildReproSteps(testInfo),
    evidence: "trace: " + traceDir + "/trace.zip\n截图: " + screenshot + "\n日志:\n" + logSnippet,
    assignee: DOMAIN_OWNER[tags.domain],
  });

  // 5. 写入报告
  console.log("[禅道] bug 已建: " + bugUrl);
  appendReport("[FAIL] " + tags.feature + " -> " + bugUrl);
});

export { expect } from "@playwright/test";
```

每个 spec 文件只需改一行 import：

```ts
// e2e/governance/sso-logout.spec.ts

+ import { test, expect } from "../_shared/hooks";  // 自动获得 fail 钩子
```

### 7.3 tag-lint：怎么写

#### 校验规则

| 规则 | 正则 | 说明 |
|---|---|---|
| @domain 存在 | @domain:(chat|orchestration|...|frontend) | 必须是预定义域（拆完前含 todo） |
| @feature 存在 | @feature:[a-z0-9-]+ | kebab-case |
| @layer 存在 | @layer:(smoke|deep|e2e) | 三档之一 |
| @severity 存在 | @severity:(high|mid|low) | 三档之一 |
| @date 存在 | @date:\d{8} | YYYYMMDD |
| 无裸 test | 所有 test(...) 必须含 5 标签 | 防遗漏 |

#### 实现：scripts/tag-lint.js

```js
const fs = require("fs");
const path = require("path");

const DOMAINS = ["chat","orchestration","execution","workflow","registry",
                  "governance","auth","sandbox","bus","persistence",
                  "observability","frontend","todo"];
const LAYERS = ["smoke","deep","e2e"];
const SEVERITIES = ["high","mid","low"];

const TAG_PATTERNS = {
  domain:   new RegExp("@domain:(" + DOMAINS.join("|") + ")\\b"),
  feature:  /@feature:([a-z0-9-]+)\b/,
  layer:    new RegExp("@layer:(" + LAYERS.join("|") + ")\\b"),
  severity: new RegExp("@severity:(" + SEVERITIES.join("|") + ")\\b"),
  date:     /@date:(\d{8})\b/,
};

const TEST_TITLE_RE = /test\s*\(\s*['"`]([^'"`]+)['"`]/g;

function lintFile(filePath) {
  const content = fs.readFileSync(filePath, "utf8");
  const errors = [];
  let match;
  while ((match = TEST_TITLE_RE.exec(content)) !== null) {
    const title = match[1];
    const line = content.slice(0, match.index).split("\n").length;
    for (const [tag, re] of Object.entries(TAG_PATTERNS)) {
      if (!re.test(title)) {
        errors.push(filePath + ":" + line + " 缺 @" + tag + " | title: " + title.slice(0,60));
      }
    }
    const dateMatch = title.match(/@date:(\d{8})/);
    if (dateMatch) {
      const d = dateMatch[1];
      const m = +d.slice(4,6), day = +d.slice(6,8);
      if (m < 1 || m > 12 || day < 1 || day > 31) {
        errors.push(filePath + ":" + line + " @date 日期非法: " + d);
      }
    }
  }
  return errors;
}

function main() {
  const e2eDir = path.resolve(__dirname, "../e2e");
  const specFiles = [];
  (function walk(dir) {
    for (const e of fs.readdirSync(dir, {withFileTypes:true})) {
      if (e.isDirectory()) walk(path.join(dir, e.name));
      else if (e.name.endsWith(".spec.ts")) specFiles.push(path.join(dir, e.name));
    }
  })(e2eDir);
  let allErrors = [];
  for (const f of specFiles) allErrors = allErrors.concat(lintFile(f));
  if (allErrors.length) {
    console.error("[tag-lint] 发现 " + allErrors.length + " 处标签问题:");
    allErrors.forEach(e => console.error("  " + e));
    process.exit(1);
  }
  console.log("[tag-lint] 全部通过, 扫描 " + specFiles.length + " 个 spec 文件");
}
main();
```

#### 三处门禁挂载

1. CI 前置（git push 时）：package.json 加 prepush 脚本 -> 标签不全的 spec 推不上去
2. 测试 skill 阶段0（每次跑测试前）：所有 d*-test skill 第0步跑 tag-lint -> 标签不全的 spec 不让跑
3. feature-test-author 生成后自检：生成 test 骨架后立即调 tag-lint 单文件校验 -> LLM 生成的用例标签不全当场打回

### 7.4 判定分层：机械断言 + LLM Judge（双层判定）

> **来源**：v2-spec-integration-e2e.md §2.3（LLM Judge 契约）+ e2e/dev-local/llm-judge.ts（已实现）

#### 为什么需要两层

智能体系统的回复是自然语言，"对不对"无法靠状态码判定。只看 HTTP 200 会漏掉"回复跑题/幻觉/格式错"；只靠 LLM Judge 又慢且不稳定。因此**机械断言抓硬错，LLM Judge 判语义**，两层 AND：

| 层 | 判什么 | 怎么判 | 速度 | 覆盖 |
|---|---|---|---|---|
| L1 机械断言 | 崩溃/超时/错误码/DOM 结构/API 状态 | `expect(res.status()).toBe(200)` / locator 断言 | 快（ms） | 确定性错误 |
| L2 LLM Judge | 回复是否"语义正确"（相关性/格式/完整性/幻觉） | 调 Judge LLM，输入 userMessage+reply+agentChain | 慢（约 5-10s） | 智能体回复合理性 |

#### Judge 凭证隔离（铁律）

| 配置 | Judge（测试侧） | 编排 LLM（被测侧） |
|---|---|---|
| 环境变量 | `GNEX_JUDGE_KEY` | `GNEX_DEEPSEEK_KEY`（或注入的 deepseek key） |
| Provider | 智谱 bigmodel.cn | DeepSeek |
| Model | `glm-5.2` | `deepseek-v4-flash` |
| 隔离状态 | 必须物理隔离，禁止复用 | 已隔离 |

> **禁止**：Judge 复用编排 LLM 凭证（会变成"自己判自己"，盲区无法发现）。这是 v2-spec-integration-e2e.md §3 的硬边界。

#### Judge 实现要点（llm-judge.ts 已具备）

- `smartSlice` 头尾折叠：保留回复头部 25% + 尾部 75%，确保多步流水线的首步产物和最终交付都被 Judge 看到
- `extractAgentChain`：从 trace 提取 agent 调用顺序，让 Judge 即使在 finalReply 被折叠时也能看到完整调用链
- 超时 90s，返回 `{verdict: pass|fail|skip, reason, category}`

#### 哪些用例该挂 Judge

- `@domain:chat` 的对话用例、`@layer:smoke` 涉及智能体回复的用例，必挂 Judge
- 纯 API/状态用例（如 RBAC 越权返回 403、迁移幂等），只用机械断言，不挂 Judge
- `@domain:auth` 等确定性强的域，以机械断言为主，Judge 按需

每个建好的 skill 必须过 3 道门禁才能交付：

2. "修复"（改断言让它 pass）

4. 检查: pass + 禅道 bug #N 可手动 resolve

三道门禁全过 = 机制质量过关，可投入日常使用。

## 十、playwright.config 关键配置

```ts
export default defineConfig({
  use: {
    trace: "retain-on-failure",      // fail 才留 trace，pass 不留
    screenshot: "only-on-failure",   // fail 截图
```

## 十三、机制如何支撑"不停迭代"

| 你要做的事 | 机制怎么支撑 | 要改 skill 吗 |
|---|---|---|
| 加一条新功能用例 | B类链路，打标签写入即可 | 不改 |
| 改一条用例的断言 | 直接编辑 .spec.ts | 不改 |
| 跑某功能的所有用例 | --grep "@feature:xxx" | 不改 |
| 跑今天新增的 | --grep "@date:今日" | 不改 |
| 给某功能加"边界场景"用例 | B类链路，同 feature 多条 test | 不改 |
| 临时只跑高危的 | --grep "@severity:high" | 不改 |
| 新模块拆出来了 | 填 @domain 取值映射表 | 改一次配置 |
| 想换切片维度（如按指派人） | 加一个 @owner 标签维度 | 改 tag-lint + 映射表 |

**根本原因**：机制是"标签 + grep"，标签是开放的。加用例 = 加标签，跑用例 = 组合标签。skill 只翻译，不持有用例清单，所以用例增减不影响 skill。
