# GNEX Core 测试体系文档

> 本文档面向**测试调用者与接手人员**，完整说明：测试如何设计、需要哪些文件、如何执行、如何判断成功。
> 测试代码（spec / hooks）由 AI 编写维护，调用者只需用自然语言下达指令。

## 第一部分：测试设计

### 1.1 设计理念

GNEX Core 采用**多维标签切面 + 分层测试**的设计。每条测试用例不靠目录归类，而是用**注释标签**标注 5 个切面维度，机器可读、可任意组合筛选。

### 1.2 五大切面（标签体系）

每个 spec 文件头部和 `test.describe` / `test` 上都标注这些标签：

| 切面 | 标签 | 含义 | 取值示例 |
|------|------|------|---------|
| **业务域** | `@domain:` | 归属的架构域（系统分层） | auth / execution / registry / governance / sandbox / bus / persistence / observability / frontend / chat / orchestration / ops |
| **测试层** | `@layer:` | 测试的深度/阶段 | smoke（冒烟）/ edge（边界）/ regression（回归）/ perf（性能） |
| **严重度** | `@severity:` | 失败影响等级 | P0（阻塞）/ P1（严重）/ P2（一般）/ P3（轻微） |
| **功能点** | `@feature:` | 具体验证的功能 | v1-标准topic恰为8个 |
| **日期** | `@date:` | 用例创建日期 | 20260713 |

**标签示例**（取自 bus-topic.spec.ts）：
```typescript
/**
 * @domain:bus
 * @layer:smoke
 */
test.describe('bus-topic Topic规范 @domain:bus @layer:smoke', () => {
  test('V2-Topic名不含高基数字段 @feature:v2-topic名不含高基数字段 @severity:P2', async () => {
```

### 1.3 功能测试 vs 全局测试

测试分两大类，通过文件命名和 domain 归属区分：

#### A. 功能测试（单域功能验证）

**特征**：聚焦单一架构域的功能点，用 `V1-Vn` 编号覆盖该域 spec 验收点。文件名通常含域名。

| 域 | 代表文件 | 验证内容 |
|----|---------|---------|
| auth（接入/认证） | auth-token-sign / auth-password / auth-sso-supplement | Token 签发、密码管理、SSO、API Key、设备会话 |
| registry（注册中心） | model-connectivity / agents / import-security / credentials | 模型连通、Agent 注册、导入安全、凭证加密 |
| governance（治理） | billing / audit / quality-gate / extension-spi | 计费精度、审计完整性、质量门禁、SPI 白名单 |
| sandbox（沙箱） | dangerous-shell / sensitive-path-hard-deny / loop-detection | 危险命令拦截、敏感路径硬保护、循环检测 |
| bus（总线） | bus-topic / bus-produce / bus-subscribe / message-bus | Topic 规范、投递可靠性、订阅隔离 |
| persistence（持久化） | migration-idempotent / isolation-four-layer / memory-l0-l4 | 迁移幂等、四层隔离、记忆分层 |
| observability（可观测） | observability-query / observability-state-plane / otel-tracing | 运营指标、状态面物化、Trace 关联 |
| execution（运行时） | d4-runtime / agent-team-new / coordinator-isolation | ReAct 循环、Checkpoint、Agent 协作 |
| frontend（前端） | adoption-feedback / artifact-preview / chat-interaction-modes | 采纳反馈、产物预览、交互模式 |

#### B. 全局测试（跨域集成 / 端到端）

**特征**：不局限于单域，验证多模块协同、架构约束、部署完整性。文件名通常含 integration / fullstack / backward 等。

| 类型 | 代表文件 | 验证内容 |
|------|---------|---------|
| 全栈端到端 | fullstack-e2e.spec.ts | 登录→对话→产物 全链路 |
| 向后兼容 | backward-compat.spec.ts | 旧数据/旧 API 兼容 |
| CI/CD 集成 | integration-cicd.spec.ts | 流水线触发、构建产物 |
| 部署拓扑 | integration-deployment.spec.ts | 容器编排、健康检查 |
| 门禁断言 | integration-gate.spec.ts | 编译/逻辑/部署/H1-H8 回归门禁 |
| 回归/性能/安全 | integration-regression-perf-sec.spec.ts | 综合回归 + 性能基线 + 安全扫描 |

#### C. 编排专项测试（D3 38 条，有独立完成证书要求）

这 4 个套件是**编排能力**的完整验证，受 `project_rules.md` 铁律约束，必须 38 条全跑、输出完成证书：

| 套件 | 文件 | 用例数 | 验证内容 |
|------|------|--------|---------|
| Intelligence Smoke | intelligence-smoke.spec.ts | 7 | 上下文记忆、主动澄清、边界诚实、相关性、错误恢复、意图演化、简洁性 |
| Deep Dialog | deep-dialog.spec.ts | 4 | 10 轮递进、采纳/忽略/反馈按钮、反馈输入框 |
| Orch Routes | （编排路由测试） | 18 | 翻译/摘要/审查/诗人/SQL/出题 委派 + 能力询问 + NO_MATCH + 模糊意图 + 风险确认 |
| Multi-Agent Pipeline | multi-agent-pipeline.spec.ts | 9 | 两阶段/三阶段流水线、决策理性（不过拆/识别复合） |

> ⚠️ D3 测试有**防偷工机制**（R1-R7）：必须列 38 条清单、禁用"代表性抽样"措辞、输出完成证书。详见 `.trae/rules/project_rules.md`。

### 1.4 测试层（@layer）的含义

| 层级 | 定位 | 触发时机 | 范围 |
|------|------|---------|------|
| **smoke** | 冒烟 | 每次部署后 | 核心路径快速验证（几分钟） |
| **edge** | 边界 | 日常回归 | 异常输入、边界条件、权限越权 |
| **regression** | 回归 | 发布前 | 已修复 bug 不复发 |
| **perf** | 性能 | 定期 | 响应时间、吞吐、资源占用 |

### 1.5 测试运行机制

```
Playwright 有头浏览器
     │
     ├─ 用例 pass → 无动作
     │
     └─ 用例 fail → hooks.ts autoSubmitBugOnFail()
              │
              ├─ 502/Bad Gateway/连接重置 → 跳过（服务问题，非 bug）
              │
              └─ 真实 fail → 提交禅道 bug
                       │
                       ├─ 从 spec 提取可复现步骤（curl 命令 + UI 操作）
                       ├─ ${BASE_URL} 解析为实际地址
                       ├─ CSS 选择器转中文名（cleanSelector）
                       ├─ <br> 换行（禅道兼容）
                       └─ 按 domain 自动指派责任人
```

## 第四部分：如何检查测试是否成功

### 4.1 运行时观察

- **有头浏览器**：Chromium 窗口弹出，可见自动操作（headed 模式）
- **控制台实时输出**：每个用例显示 pass / fail / skipped
- **bug 提交日志**：fail 时自动输出：
  ```
  [auto-bug] ✅ 已提交禅道 bug #549 → zhangxy
  [auto-bug] 链接: http://192.168.0.66:8080/zentao/bug-view-549.html
  ```

### 4.2 测试完成后的判断标准

| 信号 | 含义 |
|------|------|
| **exit code 0** | 全部 pass（含 skipped） |
| **exit code 1** | 有 fail（已自动提交 bug） |
| 控制台末尾 `X passed, Y failed, Z skipped` | 汇总 |

### 4.3 检查测试报告

```powershell
# HTML 报告（含截图、视频、trace）
start dev-local-html-report/index.html

# JSON 报告（机器可读）
type test-results\dev-local-report.json
```

### 4.4 检查提交的 bug

1. 访问禅道：http://192.168.0.66:8080/zentao/bug-browse-1.html
2. 按标题筛选 `[域名-P级]`，例如 `[auth-P1]`
3. 每个 bug 应含五段：`[域]` / `[步骤]` / `[结果]` / `[期望]` / `[证据]`
4. 确认 bug 已指派给正确责任人（见下表）

## 第五部分：关键规则与故障排查

### 5.1 502 Bad Gateway 豁免（重要）

502 / Bad Gateway / ECONNREFUSED / 连接重置 是**服务不可用**，不是代码缺陷。hooks.ts 会**自动跳过**，不提交 bug。

如大量用例因 502 失败 → dev.local 服务未启动，需重新部署：
```powershell
# 检查健康
Invoke-RestMethod "http://gnex-core.dev.local/actuator/health"
# 应返回 UP
```

### 5.2 测试前必须检查部署（铁律九）

每次测试前，验证容器创建时间晚于 develop 最新 commit：
```powershell
# 最新 commit 时间
git log -1 --format="%ci" develop
# 容器创建时间
sshpass -p "123456" ssh user@192.168.1.100 "docker inspect gnex-core-v2-dev-web --format '{{.Created}}'"
```
容器时间早于 commit → 触发 Jenkins 重新部署，等 healthy 后再测。

### 5.3 触发 Jenkins 部署

```powershell
$b64=[Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes("admin:11b0d35947e56f6cc83ac74af6f2c5471f"))
$h=@{Authorization="Basic $b64"}
$crumb=Invoke-RestMethod "http://jenkins.local/crumbIssuer/api/json" -Headers $h
$h[$crumb.crumbRequestField]=$crumb.crumb
Invoke-WebRequest "http://jenkins.local/generic-webhook-trigger/invoke?token=gnex-core-trigger" -Method Post -Headers $h -Body '{"ref":"refs/heads/develop"}' -ContentType "application/json"
```

### 5.4 常见故障

| 现象 | 原因 | 解决 |
|------|------|------|
| 浏览器不弹出 | CI 环境变量 / 僵尸进程 | `Remove-Item Env:CI`; 清理 chrome 进程 |
| 大量 502 | dev.local 未启动 | 触发 Jenkins 部署 |
| `require is not defined` | hooks.ts ESM 问题 | 已修复，确认 hooks.ts 用 `import * as fs` |
| 用例全 skipped | 端点未实现（404） | 正常，后端功能未上线 |
| bug steps 显示 `\n` 不换行 | 旧版 hooks | 确认 hooks.ts 用 `<br>` 换行 |

### 5.5 测试铁律速查

完整铁律见 `.trae/rules/project_rules.md`，核心几条：

- **铁律八**：测试发现的 bug 必须提交禅道（hooks 自动完成）
- **铁律九**：测试前必须验证容器是最新代码
- **D3 R1-R7**：38 条用例必须全跑、禁代表性抽样、输出完成证书
