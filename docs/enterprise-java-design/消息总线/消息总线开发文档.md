# gnex-bus 2.0 开发指南

> **配套**:`gnex-bus-2-architecture.md`(架构定稿)、`gnex-bus-2-topic-design.md`(Topic 规范)。本文是架构的开发落地版:架构讲"是什么/为什么",本文讲"怎么写/按什么顺序/避开哪些坑"。
> **读者**:动手写 gnex-bus 代码的开发者。
> **形态**:gnex-bus **不是消息转发 proxy**,产物是 **`gnex-bus-sdk`(jar,嵌入各业务微服务,负责投递) + RocketMQ 集群(基础设施,负责存投) + `gnex-bus-admin`(独立治理微服务,负责总览/死信/requeue/回放/监控)**。三者都直连 broker,**互不转发消息**;admin 不在投递热路径上。
> **设计主轴(能力 vs 机制)**:SDK 尽量**暴露 RocketMQ 的能力**(异步/批量/定时/事务/顺序/过滤/广播/位点起点/按键查),但**隐藏它的机制**(push⇄pop、队列选择、rebalance、offset 提交时机、listener 类型)——机制封在 transport 内部,契约保持稳定。

---

## 0. 开工前

### 0.1 必读

- **架构文档全文**,尤其 §3 对外契约、§4 生产语义、§5 消费语义、§7 RocketMQ 映射。本文不重复"为什么",只讲"怎么做"。
- 六条**不可违背的红线**(违反会返工,详见文末表):
  1. **bus 是纯管道**:任何业务语义(调度、租户路由、同步等待)都不得进 bus。bus 只认 `topic` + `orderKey` + `filter` + `properties` + `payload`。
  2. **payload 不透明**:bus 代码里**严禁**解析 payload(不许 `JSON.parse`、不许读 payload 字段)。payload 是 String,原样存原样投。
  3. **原语执行不走总线**:不要为 Action/Observation 建 topic 或通道——原语执行走 WebSocket(架构 §9)。bus 的职责到"沙箱就绪"为止。
  4. **可靠性靠 RocketMQ 原生**:重试/退避/死信交给 RocketMQ 原生(延迟等级 + `%DLQ%`),**不许自建消息状态表、不许自建 scheduler 重投**。bus 只配策略参数。
  5. **投递不做 proxy**:SDK 直连 broker,不起独立进程转发。
  6. **admin 不碰投递**:admin 只做治理(status/requeue/pause/回放),不写 produce/subscribe 投递路径。

### 0.2 前置依赖

| 依赖                  | 状态   | 说明                                                         |
| --------------------- | ------ | ------------------------------------------------------------ |
| 架构文档定稿          | ✅      | 本文档的依据                                                 |
| RocketMQ 5.x 环境     | 需准备 | broker 用 5.x(timer message / Controller 选主 / Pop);客户端用 classic remoting `rocketmq-client` |
| `gnex-contracts` 模块 | 可编译 | 契约(信封 + 接口)落这里                                      |

> 注:bus **不存消息**(消息/死信/重试全在 broker)。所以**不强依赖数据库**——admin 侧可选的少量治理元数据(订阅 paused 状态 / requeue 审计)用不用由团队定(Phase 5)。

### 0.3 开发顺序(对应架构 §13 落地路径)

严格按此顺序,不可跳:

```
Phase1 契约 → Phase2 SDK core(信封/校验/metrics) → Phase3 InProcess transport
  → Phase4 RocketMQ transport(produce 全族 + subscribe 全维度 + retry/DLQ)
  → Phase5 admin(总览/死信/requeue/回放/订阅元数据) → Phase6 接入业务服务 → Phase7 生产验证
```

## Phase 1:契约层(contracts)

**目标**:把信封 + 双接口写进 `gnex-contracts`,让所有调用方能编译依赖。

**落点**:`gnex-contracts/src/main/java/com/gnex/contracts/bus/`

### 1.1 MessageEnvelope(统一信封,10 字段)

```java
package com.gnex.contracts.bus;

public record MessageEnvelope(
    String msgId,                   // broker 回填(produce 时 null,consume 时已填);幂等/关联用
    String dedupId,                 // 可选,机器幂等键(生产者重试填同一值防重投)
    String keys,                    // 可选,业务检索键 → RocketMQ msg keys(admin queryByKey 用)
    String topic,                   // 必填,标准 8 topic 之一(见 topic 文档)
    String orderKey,                // 必填,{tenant}:{entity};RocketMQ 映射为 shardingKey
    String schemaVersion,           // 必填,payload schema 版本(如 "1.0.0")
    String payload,                 // 必填,业务正文(bus 不解析),≤256KB,超限走 blob:// 旁路
    String filter,                  // 可选,过滤表达式;filterType=TAG 时映射 Tag
    Map<String, String> properties, // 必填,tenantId/traceId/requestId/sessionId 等
    Instant timestamp               // 发送时间(produce 时 SDK 填充)
) {
    public MessageEnvelope {  // 紧凑构造器:校验必填
        Objects.requireNonNull(topic, "topic 必填");
        Objects.requireNonNull(orderKey, "orderKey 必填");
        Objects.requireNonNull(schemaVersion, "schemaVersion 必填");
        Objects.requireNonNull(payload, "payload 必填");
        if (properties == null) { properties = Map.of(); }
    }
}
```

> **红线**:信封字段固定,不要加 `actionType`/`messageType` 之类——业务类型是 payload 的事,信封不区分。
> **中间件无关**:调用方只传 `orderKey`/`filter`,RocketMqTransport 内部翻译(orderKey→shardingKey、filter→Tag/SQL92)。contracts 里**不出现** shardingKey/Tag 等中间件术语。
> **keys vs dedupId**:`keys` 给人按键检索,`dedupId` 给机器幂等去重,互不替代(架构 §3.1)。

### 1.2 BusInterface(热路径,业务微服务只依赖它)

```java
package com.gnex.contracts.bus;

public interface BusInterface {
    // —— 生产:送达保证 ——
    ProduceResult produce(MessageEnvelope message);                         // 同步,等 broker ack
    CompletableFuture<ProduceResult> produceAsync(MessageEnvelope message); // 异步,高频不阻塞
    // —— 生产:批量 ——
    List<ProduceResult> produceBatch(List<MessageEnvelope> messages);       // 同 topic 批量
    // —— 生产:定时(任意 Duration / 绝对时间点,底层 5.x timer message)——
    ProduceResult produceScheduled(MessageEnvelope message, Duration delay);
    ProduceResult produceAt(MessageEnvelope message, Instant deliverAt);
    // —— 生产:事务消息(RocketMQ 独有,替代业务自建 outbox)——
    ProduceResult produceInTransaction(MessageEnvelope message, LocalTransactionExecutor executor);
    // —— 消费:声明式订阅(维度在 SubscribeRequest)——
    Subscription subscribe(SubscribeRequest request, MessageHandler handler);
    void unsubscribe(String subscriptionId);
}
```

> **★不做 `produceOneway`**:当前 8 topic 无可接受静默丢失的消费方(指标走 Micrometer 不过 bus),暴露即脚枪(架构 §3.3)。真出现可丢高频 topic 再加。
> **异常契约**:`produce`/`produceBatch` broker 不可达抛 `BusUnavailableException`(运行时);`produceAsync` 失败走 Future 异常通道;背压/超大消息返回 `accepted=false`(不抛)。

### 1.3 订阅请求 / 消费回调 / 事务执行器

```java
public record SubscribeRequest(
    String topic,
    String consumerGroup,          // 角色级(sched-cg/sync-cg/...),见 topic 文档 §4。不带 tenant
    String consumerName,
    String filterExpression,       // TAG: "READY||FAILED";SQL92: "level>3"
    FilterType filterType,         // TAG(默认) | SQL92(broker 需 enablePropertyFilter)
    OrderMode orderMode,           // CONCURRENT(默认) | ORDERLY(同 orderKey 强顺序)
    ConsumeModel consumeModel,     // CLUSTERING(默认) | BROADCASTING(预留能力位)
    ConsumeFrom consumeFrom,       // LAST_OFFSET(默认) | FIRST_OFFSET | TIMESTAMP
    Instant consumeFromTime,       // consumeFrom=TIMESTAMP 时生效
    int maxBatchSize               // 批量消费单批上限(典型 100)
) {}

public enum FilterType   { TAG, SQL92 }
public enum OrderMode    { CONCURRENT, ORDERLY }
public enum ConsumeModel { CLUSTERING, BROADCASTING }
public enum ConsumeFrom  { LAST_OFFSET, FIRST_OFFSET, TIMESTAMP }

// handler 处理整批,同步返回(★无 AckHandle)
public interface MessageHandler {
    ConsumeResult handle(List<ReceivedMessage> messages);
}
public enum ConsumeResult { SUCCESS, RETRY }

public record ReceivedMessage(
    String messageId, MessageEnvelope envelope, Instant deliveredAt, int attempt
) {}

// 事务消息执行器
public interface LocalTransactionExecutor {
    LocalTxState execute(MessageEnvelope message);   // half-message 发出后执行本地事务
    LocalTxState check(MessageEnvelope message);      // broker 回查未决事务
}
public enum LocalTxState { COMMIT, ROLLBACK, UNKNOWN }

// 配套 DTO
public record ProduceResult(String messageId, boolean accepted, String reason) {}
public record Subscription(String subscriptionId, String topic, String consumerGroup, String consumerName) {}
```

> **★为什么没有 AckHandle / 拉模型**:架构 §5 明确放弃了早期稿的 `AckHandle`(ack/nack/heartbeat)和 `consume`/`consumeBatch` 拉模型。`MessageListener` 处理完一批**同步返回** `SUCCESS`/`RECONSUME_LATER` 正是 RocketMQ 原生语义;用 `CompletableFuture` 阻塞 listener 把 push 拧成 pull、再自造 per-message heartbeat 是在与中间件对抗。**长任务改用"快速接管 + 异步执行"范式(§Phase6 / 架构 §5.2),不持有 broker ack。**

## Phase 2:SDK core(信封校验 + Topic 注册校验 + metrics)

**目标**:在 transport 之上,做与中间件无关的入口校验和埋点。

**落点**:`gnex-bus-sdk/.../bus/`

- **信封校验**:必填字段、`payload` ≤256KB(超限 `accepted=false`,提示走 `blob://` 旁路)、`properties.tenantId`/`traceId` 存在性。
- **Topic 注册校验**:`topic` 必须是标准 8 个之一(见 topic 文档),未注册直接拒绝。
- **属性注入**:`timestamp` 填充;缺失的 `traceId` 按约定生成或拒绝。
- **背压闸门**:见 §Phase4 生产侧,`accepted=false` 只来自 payload 超限 / 本地 outbox 满。
- **metrics**(Micrometer):`bus_produce_total{topic,tenant}`、`bus_produce_failed_total{topic,reason}`、`bus_consume_total`、`bus_consume_duration_seconds`、`bus_backpressure_rejected_total`、`bus_handler_retry_total`(架构 §11)。

> **不解析 payload**:校验只看信封字段和大小,绝不读 payload 内容。

## Phase 3:InProcess transport(dev 用,先写它好联调)

**目标**:内存实现 transport SPI,让 produce/subscribe 闭环在无 RocketMQ 时可测。

**落点**:`gnex-bus-sdk/.../bus/transport/`

### 3.1 transport SPI(内部接口,非 contracts)

```java
package com.gnex.bus.transport;

public interface MessageBusTransport {
    String send(MessageEnvelope envelope);                                   // 同步
    CompletableFuture<String> sendAsync(MessageEnvelope envelope);           // 异步
    List<String> sendBatch(List<MessageEnvelope> envelopes);                 // 批量
    String sendScheduled(MessageEnvelope envelope, Duration delay);          // 定时(相对/绝对统一转 Duration)
    String sendInTransaction(MessageEnvelope envelope, LocalTransactionExecutor exec); // 事务
    Subscription subscribe(SubscribeRequest request, MessageHandler handler);// 声明式订阅
    void unsubscribe(String subscriptionId);
    String transportName();   // "inprocess" / "rocketmq"
}
```

> **SPI 只管投递/订阅**,不管重试计数、退避、死信判定——那些是 RocketMQ 原生(Phase4 只配参数)。handler 返回 `RETRY` 是触发原生重试的唯一入口。

### 3.2 InProcessTransport

```java
@Component
@ConditionalOnProperty(prefix = "gnex.message-bus", name = "mode", havingValue = "inprocess", matchIfMissing = true)
public class InProcessTransport implements MessageBusTransport {
    // 内存 BlockingQueue,按 (topic, consumerGroup) 分队列
    // subscribe:后台线程按 orderMode 决定串行(ORDERLY,同 orderKey 保序)/并发(CONCURRENT)投递给 handler
    // handler 返回 RETRY → 重入队 attempt+1,超阈值 → 死信队列(模拟 RocketMQ 原生重试/死信,供 dev 测)
    // sendScheduled → 延迟入队(ScheduledExecutorService)
    // sendInTransaction → 执行 executor.execute();COMMIT 才入队,UNKNOWN 触发一次 check()
    // filterType=TAG/SQL92 → 内存里做等价过滤(dev 简化实现)
}
```

> **InProcess 是测试替身**:模拟原生重试/死信/定时/事务的**逻辑**,但测不出 RocketMQ 真实行为。真实验证必须切 `mode=rocketmq`(见 Phase7)。

## Phase 4:RocketMQ transport(生产环境实现)

**目标**:实现 `MessageBusTransport` 的 RocketMQ 版本,把架构 §7 映射表逐条兑现。

**落点**:`gnex-bus-sdk/.../bus/transport/RocketMqTransport.java`

### 4.1 生产侧:一族 send 映射到 RocketMQ

| SPI                 | RocketMQ 实现                                                |
| ------------------- | ------------------------------------------------------------ |
| `send`              | `producer.send(msg)` 同步                                    |
| `sendAsync`         | `producer.send(msg, SendCallback)`,回调 complete `CompletableFuture` |
| `sendBatch`         | `producer.send(Collection<Message>)`,同 topic 批量           |
| `sendScheduled`     | 5.x timer message:`msg.setDeliverTimeMs(now + delay)`(任意 Duration,不用 18 级 DelayLevel) |
| `sendInTransaction` | `TransactionMQProducer` + `TransactionListener`(executeLocalTransaction → executor.execute;checkLocalTransaction → executor.check) |

信封字段映射(架构 §7):`orderKey`→shardingKey(`MessageQueueSelector` 选队列)、`filter`+`TAG`→msg Tag、`filter`+`SQL92`→订阅侧 SQL92 表达式、`keys`→`msg.setKeys()`、`payload`→msg body、`properties`→msg properties、`msgId`→broker 分配后回填 `ProduceResult`。

```java
// orderKey → shardingKey → 固定队列(保证同 key 顺序)
Message msg = new Message(env.topic(), env.filter() /*Tag*/, env.payload().getBytes(UTF_8));
if (env.keys() != null) { msg.setKeys(env.keys()); }
env.properties().forEach(msg::putUserProperty);
producer.send(msg, (mqs, m, arg) -> {
    int idx = Math.abs(arg.hashCode()) % mqs.size();
    return mqs.get(idx);
}, env.orderKey());
```

### 4.2 消费侧:声明式 subscribe,按维度构建 consumer(★无桥接)

因为 handler 同步返回,消费实现就是"注册 listener → 调 handler → 映射返回状态",**不需要 push→pull 桥接**:

```java
public Subscription subscribe(SubscribeRequest req, MessageHandler handler) {
    DefaultMQPushConsumer consumer = new DefaultMQPushConsumer(req.consumerGroup());
    consumer.setNamesrvAddr(nameserver);
    consumer.setConsumeThreadMax(threadMaxOf(req.topic()));          // 按 topic 区分(见 §4.4)
    consumer.setConsumeMessageBatchMaxSize(req.maxBatchSize());      // 批量投递给 handler
    consumer.setPullThresholdForQueue(1000);
    consumer.setMessageModel(map(req.consumeModel()));              // CLUSTERING / BROADCASTING
    consumer.setConsumeFromWhere(map(req.consumeFrom()));           // LAST / FIRST / TIMESTAMP
    if (req.consumeFrom() == ConsumeFrom.TIMESTAMP) {
        consumer.setConsumeTimestamp(format(req.consumeFromTime()));
    }
    // 过滤:TAG 用 selectorByTag;SQL92 用 selectorBySql92(broker 需 enablePropertyFilter)
    if (req.filterType() == FilterType.SQL92) {
        consumer.subscribe(req.topic(), MessageSelector.bySql(req.filterExpression()));
    } else {
        consumer.subscribe(req.topic(), req.filterExpression() == null ? "*" : req.filterExpression());
    }

    // ★orderMode 决定 listener 类型,调用方不接触 RocketMQ 类型
    if (req.orderMode() == OrderMode.ORDERLY) {
        consumer.registerMessageListener((MessageListenerOrderly) (msgs, ctx) ->
            invoke(handler, msgs)
                ? ConsumeOrderlyStatus.SUCCESS
                : ConsumeOrderlyStatus.SUSPEND_CURRENT_QUEUE_A_MOMENT);
    } else {
        consumer.registerMessageListener((MessageListenerConcurrently) (msgs, ctx) ->
            invoke(handler, msgs)
                ? ConsumeConcurrentlyStatus.CONSUME_SUCCESS
                : ConsumeConcurrentlyStatus.RECONSUME_LATER);
    }
    consumer.start();
    return new Subscription(newId(), req.topic(), req.consumerGroup(), req.consumerName());
}

// 整批调 handler:全成功→true;返回 RETRY 或抛异常→false(整批重投)
private boolean invoke(MessageHandler handler, List<MessageExt> msgs) {
    try {
        List<ReceivedMessage> batch = msgs.stream().map(this::toReceived).toList();
        return handler.handle(batch) == ConsumeResult.SUCCESS;
    } catch (Exception e) {
        log.warn("handler 异常,整批重投", e);
        return false;
    }
}
```

> **整批判定**:RocketMQ 一批只能返回一个状态,无"部分成功"。返回 `RETRY`/抛异常 → 整批(含已处理的)重投 → 靠消费者幂等吸收(§Phase6 幂等指引)。这是 RocketMQ 能力边界,不是缺陷。
> **pause/resume 落地**:admin 改治理状态后,SDK 经**低频通道**(启动拉一次 + 定期轮询/配置中心)拿到 paused,对 consumer 执行 `suspend()`/`resume()`,不逐条丢消息(架构 §10.3)。治理面故障时默认继续消费。

### 4.3 可靠性:只配参数,不自建状态机

```java
@ConfigurationProperties("gnex.message-bus.retry")
public class RetryPolicy {
    private int maxReconsumeTimes = 16;   // 原生重试次数(延迟等级 1s~2h),传给 consumer
}
```

重试/退避/死信全由 RocketMQ 原生做:handler 返回 `RETRY` → `RECONSUME_LATER` → 原生延迟重试 → 耗尽进 `%DLQ%{group}`。**代码里不许出现 `MessageStateStore`/`scheduler`/`markRetrying`。**

### 4.4 配置

```yaml
gnex:
  message-bus:
    mode: rocketmq
    rocketmq:
      name-server: ${ROCKETMQ_NAMESERVER}
      producer-group: gnex-bus-producer
      # 按 topic 性质区分消费线程数,不调会成吞吐瓶颈(架构 §5 备注)
      consume-thread-max:
        sandbox.request: 64      # 控制类,低频
        agent_events: 256        # 事件类,高频(64 仅 ~1280 msg/s,256 达 ~5K)
        a2a.delegate: 128
        a2a.response: 128
        audit_log: 64
    payload:
      max-bytes: 262144
    retry:
      max-reconsume-times: 16
```

### 4.5 验收

- [ ] 启动连上 RocketMQ,`produce`/`produceAsync`/`produceBatch` → subscribe 闭环
- [ ] 同 `orderKey` + `ORDERLY`:连发 10 条,消费顺序不变
- [ ] `CONCURRENT`:不同 orderKey 可并发/乱序
- [ ] 同组分担 / 异组各收全量(sync-cg + verify-cg 订阅 agent_events 都不漏)
- [ ] `produceScheduled(任意 Duration)` / `produceAt(时间点)` 按时投递
- [ ] `produceInTransaction`:executor ROLLBACK 消息不可见;UNKNOWN 触发 broker 回查 check()
- [ ] `filterType=SQL92` 过滤生效(broker 开 enablePropertyFilter)
- [ ] handler 返回 `RETRY` → `%RETRY%{group}` 延迟重试 → 耗尽进 `%DLQ%{group}`
- [ ] `consumeFrom=TIMESTAMP` 从指定时间起消费

## Phase 5:admin(独立治理微服务)

**目标**:实现 `gnex-bus-admin`——总览 / 死信治理 / requeue / 回放 / 消息检索 / 订阅治理 / 监控。**admin 不存消息、不投递消息**,查询直打 broker 原生 API。

**落点**:`gnex-bus-admin/`

### 5.1 治理实现要点

- **总览 / 背压**:读 broker 的 topic lag、DLQ 数、consumer QPS;`outboxRejected` 从 SDK metrics 聚合。
- **死信治理**:`listDeadLetters` 扫 `%DLQ%{group}`(broker 原生支持分页);`requeue` 把死信重新 `send` 回正常 topic,**必须审计**(操作人/时间/目标/结果)。
- **消息检索**:`queryById`→broker viewMessage;`queryByKey`→broker `queryMsgByKey`(依赖信封 `keys`);`queryByTimeRange`→按时间窗口查,受 `limit` 约束(broker 不是 OLTP,不做无界扫)。
- **位点回放**:`resetOffsetByTime`→broker `resetOffsetByTimestamp`,用于回放/跳毒消息,**必须审计 + 操作确认**。
- **进度 / 路由**:`consumerProgress`→各队列 offset/lag;`topicRoute`→队列在 broker 的分布。
- **audit_log 死信自动归档**:定时扫 `%DLQ%`,audit_log 死信自动物化到检索库(不靠人 requeue),保证 90 天合规;其他 topic 仅告警等人处理(架构 §10.2)。

## Phase 6:接入业务服务

### 6.1 沙箱生命周期(架构 §9)

```
agent produce sandbox.request(properties.requestId)
  → sandbox 消费,启动沙箱,produce sandbox.events(filter=SANDBOX_READY, requestId)
  → agent subscribe sandbox.events,handler 按 requestId 关联,建立 WebSocket
```

> 原语执行走 WebSocket,不走 bus。bus 职责到"沙箱就绪"为止。

### 6.2 请求-回应关联(声明式 subscribe 下)

沙箱就绪等待、A2A 回应配对本质是"发一条 → 等一条同 requestId 回来"。声明式 subscribe 下,调用方挂常驻 handler,自己在进程内维护 `requestId → CompletableFuture` 关联表,handler 收到就 resolve;超时按失败,迟到的孤儿回应按 requestId 判断"是否还在等",不在等就丢弃 + 记审计。

### 6.3 长任务范式(不持有 ack)

```
收到消息 → 校验 tenant/schema → 写本地任务表/可靠队列 → handler 返回 SUCCESS(可靠接管)
  → 异步执行长任务 → 通过 a2a.response / sandbox.events 发结果
```

"写本地任务表"失败则 handler 返回 `RETRY`,让 RocketMQ 重投。

### 6.4 幂等指引(消费者责任,不在 bus)

bus 承诺 at-least-once、不去重。消费者用 `msgId` 或 `requestId` 幂等:高频 topic 用 Redis `SETNX`;低频用唯一索引 `ON CONFLICT DO NOTHING`。批量消费也必须按条去重(整批重投时已处理的会重来)。

### 6.5 强一致场景用事务消息

`cost_events`(计费)、`audit_log`(合规)需要"本地库写 + 发消息"原子性时,用 `produceInTransaction`,不要各自造 outbox。

## Phase 7:生产验证

RocketMQ 环境专项(InProcess 测不出):

```
1. mode=inprocess:produce → subscribe → SUCCESS 闭环;RETRY → 重投 → 死信(测替身)
2. 切 mode=rocketmq,重跑上述
3. handler 返回 RETRY → 看 %RETRY%{group} 延迟重试
4. 耗尽 maxReconsumeTimes → 看 %DLQ%{group}
5. admin requeue → 死信重投回正常队列
6. ORDERLY:同 orderKey 严格保序;毒消息队头阻塞 → maxReconsumeTimes 后进 DLQ 放行
7. 异组独立:sync-cg + verify-cg 各订阅 agent_events,各收全量
8. produceInTransaction:本地事务 ROLLBACK/UNKNOWN 回查路径
9. resetOffsetByTime 回放
```

验收底线(架构 §13):SDK 不解析 payload、不存正常消息正文、不实现全局 retry 状态机;admin 不参与投递;长任务 handler 不持有 broker ack;A2A 消息显式带目标路由字段。

## 开发者红线(写代码前贴墙上)

| 红线                                         | 表现                                                       | 后果                                                |
| -------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------- |
| **bus 解析 payload**                         | `JSON.parse(envelope.payload())` / 读 payload 字段         | 破坏纯管道,违反架构 §3                              |
| **建 actions/observations topic 或原语通道** | 为原语执行建 topic / WebSocket                             | 原语走 WebSocket(架构 §9)                           |
| **自建消息状态机**                           | `MessageStateStore` / scheduler 重投 / `markRetrying`      | 违反"broker 为真相源",双写不一致                    |
| **可靠性执行逻辑进 transport**               | 自写 retryCount/backoff                                    | 应由 RocketMQ 原生,transport 只配 maxReconsumeTimes |
| **bus 存消息到 DB**                          | 建 `agent_message_bus` 消息状态表                          | 违反"broker 为真相源"                               |
| **暴露 AckHandle / 拉模型**                  | BusInterface 加 ack/nack/heartbeat 或 consume/consumeBatch | 与中间件对抗,架构 §5 已废弃                         |
| **暴露 produceOneway**                       | 加单向不等 ack 的发送                                      | 无合法消费方,静默丢消息脚枪                         |
| **subscribe 语义泄露调度**                   | BusInterface 加 awaitObservation 等同步等待                | 调度语义泄露进 SDK,架构 §3.3                        |
| **消费组带 tenant**                          | `{role}_{tenant}` 命名消费组                               | 万级场景消费组爆炸,用角色级(topic 文档 §4)          |
| **bus 做投递 proxy**                         | 起独立进程转发到 broker                                    | 集群化变有状态,投递必须 SDK 直连                    |
| **admin 投递/转发消息**                      | admin 写 produce/subscribe                                 | admin 只治理,不在热路径                             |
